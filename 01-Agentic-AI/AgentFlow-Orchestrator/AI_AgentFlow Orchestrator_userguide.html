🤖 AgentFlow Orchestrator — Dynamic Multi-Agent Workflow & Skill Orchestration Platform — From "I want to…" to a Finished, Verified Result, Hands-Free

FastAPI + Google ADK + React: a generic agent orchestration platform. You type an intent ("convert this CSV to Excel", "research 5 tools and compare them"), an LLM planner writes a structured multi-agent plan, you approve it, an orchestrator runs the agent DAG with real tools (Python, files, web, HTTP), an evaluator scores the result, and successful workflows can be saved as reusable versioned skills. No hard-coded workflows — the same engine handles any task, because the plan is generated per intent.

The 30-second pitch

Most "AI agent" demos are one chatbot with one prompt. Ask it to do something different and it improvises — no structure, no verification, no memory of what worked.

AgentFlow Orchestrator is not a chatbot — it's a workflow operating system for agents. You state a goal in plain language. An Intent Parser classifies it (data analysis? research? QA?), a Skill Discovery layer checks whether a proven workflow already exists, and an LLM Planner otherwise generates a structured plan: how many agents, each one's goal, which tools it may use, and who depends on whom. You approve the plan before anything runs — then an Orchestrator executes the agent graph (sequential, parallel, retry), with a Policy Engine pausing for human approval before any external or destructive action. When it finishes, an Evaluator scores the output against the plan's criteria and can trigger automatic replanning. Every successful workflow can be saved as a versioned skill — and the next similar request reuses it instead of re-planning from scratch. All agents run on gpt-oss:120b via Ollama Cloud through Google ADK + LiteLLM, with a React workspace UI showing the plan, live agent activity, approvals and the scored result.

The line that matters: intent in → plan → approval → DAG execution → evaluation → reusable skill. Nothing is hard-coded; the platform is the product.

The one-line principle

🧩 Plans are data, not prompts

The planner emits a validated PlanSpec (Pydantic): agent list, tool list, dependency edges, evaluation criteria, cost/time estimates. Free-form LLM text never drives execution — the orchestrator only trusts the structured, validated plan.

🛡️ Permissions gate every action

Each tool carries a permission level — READ, WRITE, EXTERNAL_ACTION, DESTRUCTIVE. Anything external or destructive triggers a human approval gate: execution pauses, an approval card appears in the UI, and the workflow resumes only when you decide.

♻️ Success becomes a skill

A workflow that worked (agents, tools, DAG, evaluation criteria) can be frozen into a .skill.yaml / .skill.zip with semantic versioning. Next time, skill discovery finds it — keyword matching today, recommendations ranked by usage and success rate — and the plan is reused instead of regenerated.

What is this project?

AgentFlow Orchestrator is a digital project manager with a team of on-demand AI workers. You describe what you want in one sentence; it figures out how to do it, shows you the plan for sign-off, marshals the right specialists, checks the quality of the result, and remembers successful recipes for next time.

Instead of writing prompts and gluing tools yourself, you simply:

  1. Type your goal — "Convert this CSV into an Excel file", "Research 5 AI testing tools and compare them"
  2. Review the plan — who will do what, with which tools, estimated cost and time — and approve it
  3. Watch execution — each agent lights up as it runs, with its tool calls and duration
  4. Get a verified result — an evaluation badge shows the score against the plan's criteria
  5. Optionally save the workflow as a skill so the next similar request is instant

Think of an architecture firm: you bring a brief ("I want a two-storey house"), an architect (the planner) draws up plans, you approve the blueprints before construction, a site manager (the orchestrator) coordinates the builders (agents) in the right order, an inspector (the evaluator) checks the result against spec, and the finished design goes into a catalogue (the skill library) so the next client with similar needs starts from a proven template.

The 5-step loop

1

Describe — don't program

State the goal in one sentence; attach files if needed. No workflow DSL, no node editor.

The intent parser immediately classifies the request — data_analysis, research, qa, coding, document, business, automation or other — and that classification later feeds model routing (simple tasks get the fast model; complex ones the reasoning model).

2

Reuse before rebuild

Skill discovery is the first stop; the LLM planner is only asked when nothing matches well enough.

Discovery is keyword-based in this MVP (name + description + tags), with a 0.5 reuse threshold. The recommender goes further: it ranks by match score, past usage, success rate and recency, and shows you why each skill was recommended. If several skills partially match, the planner can compose them into one workflow.

The one rule that matters: the user approves every plan before execution — and any agent whose plan involves EXTERNAL_ACTION tools (web search, HTTP) triggers a second, mid-flight approval gate. Autonomy stops at the permission boundary.
3

Plans you can read

A plan is a contract: agents, goals, tools, dependencies, criteria, cost, time.

A simple request ("convert this CSV") produces exactly one agent — the planner is explicitly instructed to use the minimum number of agents. A complex request ("research 5 tools and compare") produces 5 parallel researchers feeding a comparison agent feeding a report writer. The plan card renders this as a list of agent boxes with tool chips and a "Needs Approval" badge where relevant.

Request shapeWhat the planner tends to produce
Single file conversion1 agent · file_reader + file_writer · ~10s · ~$0.01
Sales data analysisdata_analyst → report_writer · python_executor · ~2 min
Multi-source researchN parallel researchers → comparator → report · web_search (gated) · ~3 min
4

Execution you can see

Every agent start, tool call and completion is an event, stored and streamed to the UI.

The backend emits AGENT_STARTED, TOOL_STARTED/COMPLETED, AGENT_COMPLETED/FAILED, HUMAN_APPROVAL_REQUIRED and more — the frontend polls and turns them into the activity cards you watched in step 3. Agents at the same dependency level run in parallel; a failed agent retries (up to 3 attempts); you can cancel a running execution from the UI/API.

5

Judged, then remembered

Success is measured, not assumed — and success is worth freezing into a skill.

The evaluation engine scores each criterion in the plan (completeness = did all agents finish, accuracy = no failures, format = non-empty outputs, relevance = output exists), averages them, and compares to the threshold. Pass → the UI offers to save the workflow as a versioned skill. Fail → the replanner feeds the failure reasons back to the planner for a corrected plan (max 2 replans — no infinite loops).

Tips for best results

Do
  • Give absolute file paths — the plan prompt injects them verbatim; C:\Temp\data.csv works, "my file somewhere" doesn't
  • Read the plan before approving — it's the contract; agent count, tools and criteria are all visible
  • Watch the evaluation badge — score 100% with real criteria means the output was structurally verified
  • Save good workflows as skills — the next matching intent skips planning entirely
  • Set SERPAPI_API_KEY in .env — the web_search tool auto-detects Serper/SerpApi/Brave keys; without one it returns a polite "configure me" note
Avoid
  • Don't expect the planner to guess paths it was never given — vague intents produce vague plans
  • Don't approve plans whose tools you didn't mean to grant — EXTERNAL_ACTION agents pause again for approval anyway, but READ/WRITE tools run without a second gate
  • Don't run two heavy executions concurrently on the free Ollama tier — the cloud model queues and both slow down
  • Don't edit the SQLite file mid-run — execution state is persisted there; external edits confuse recovery

Frequently asked questions

Do I need to know AI or programming to use this?

No. If you can write a task request, you can drive it. The plan card is deliberately plain-language: agent names, goals and tool chips. The evaluation badge gives you a quality check without reading any logs. Programming only matters if you want to add tools or skills of your own.

Is this just a chatbot with extra steps?

No — the difference is structure. A chatbot's answer is unverified prose. Here the LLM's output is a validated JSON plan, execution is a persisted state machine with events, and the result is scored by an evaluator against declared criteria. You can pause, reject, replan or audit any part.

What happens if an agent fails mid-workflow?

Three safety nets: the agent retries (up to 3 attempts), the orchestrator marks it failed and stops dependents, and the evaluation engine records the failure — triggering the replanner, which regenerates the plan with the failure context attached. After 2 replans the task fails honestly rather than looping.

Where do skills come from?

Three ways: saved from a successful run (the platform converts the plan into a SkillSpec), authored as YAML (like the 3 built-ins: csv-to-excel-converter, document-summarization, web-research), or imported as .skill.zip — which is validated, security-scanned and previewed before you approve installation.

System overview

The backend is a FastAPI application wrapping a Google ADK runner. Agents are ADK LlmAgents whose tools are plain Python callables wrapped in FunctionTools; every LLM call goes through LiteLLM to Ollama Cloud's OpenAI-compatible endpoint. State lives in SQLite via SQLAlchemy (async), execution flows through a hand-built DAG engine, and a React/Zustand frontend renders the whole lifecycle. Planning and execution are strictly separated: the planner has zero ability to run tools, and the orchestrator never talks to the LLM about what to do — only the validated plan.

The core loop, in code

Every request walks the same pipeline. The interesting part is that three different planners can produce the plan — skill reuse, LLM generation, or the replanner — and downstream nothing knows or cares which: 

# POST /api/plans  (backend/app/api/routes_plans.py)
matched = await discover_skills(task.intent, db)      # 1. search skills
if matched and matched[0].score > 0.5:
    agent_specs = parse_agent_specs_from_yaml(spec_data)   # 2a. reuse
    plan_data = PlanSpec(task_id=task.id, agents=[...],
                         workflow=spec_data["workflow"], ...).model_dump()
else:
    plan_spec = await planner.create_plan(            # 2b. LLM planner
        task_id=task.id, intent_text=task.intent)

# POST /api/executions — fire-and-forget background task
asyncio.create_task(_run_orchestration())             # 3. execute + evaluate
#   orchestrator.execute_with_evaluation():
#     execute → evaluate → if fail & replans left → replanner → execute again
Why fire-and-forget? Planning via a 120B reasoning model takes tens of seconds and execution longer. The endpoint creates the execution record, returns its ID immediately, and the frontend polls GET /api/executions/{id} + the events endpoint to animate the timeline.

The PlanSpec contract

This Pydantic model (app/models/plan_schema.py) is the single interface between planning and execution. If it validates, the orchestrator can run it — no exceptions for "the LLM wrote something weird": 

class PlanSpec(BaseModel):
    task_id: str
    objective: str
    summary: str = ""
    agents: list[AgentSpec]          # full specs, not IDs
    workflow: WorkflowSpec           # type + nodes + edges
    memory: MemorySpec               # working / long-term flags
    evaluation: EvaluationSpec       # criteria + threshold (default 0.7)
    permissions: dict
    estimated_cost: float
    estimated_duration_seconds: int
    requires_approval: bool = True
    matched_skills: list[str] = []

class AgentSpec(BaseModel):
    id: str; name: str; goal: str
    tools: list[str] = []            # registry IDs
    dependencies: list[str] = []     # agent IDs — forms the DAG
    max_iterations: int = 5
    max_tool_calls: int = 20
    timeout_seconds: int = 300
    requires_human_approval: bool = False

The planner LLM never outputs this directly — it fills a simpler, LLM-friendly PlannerOutput schema (agent id/name/goal/tools/dependencies), and plan_validator.py upgrades and verifies it: unknown tool IDs, dangling dependencies and cycles all fail loudly before any agent exists.

DAG orchestration details

orchestrator/dag.py builds an ExecutionDAG from the plan's agent specs: nodes from AgentSpec.id, edges from dependencies. Levels are computed with Kahn's algorithm — level 0 has no dependencies, level N is one past its deepest dependency — and agents sharing a level run concurrently via asyncio.gather. A DFS back-edge check rejects cycles at construction: 

levels = dag.get_execution_levels()     # e.g. [["research_1".."research_5"], ["comparator"], ["reporter"]]
for level in levels:
    results = await asyncio.gather(*[run_agent(aid) for aid in level])
# failed agent → retry up to 3 attempts → still failing → level aborted → evaluation sees it

Tool security & the policy engine

Tools are registered with a permission level, and the policy engine (policy/engine.py) evaluates each agent before it runs: an agent whose tools include anything above WRITE — or which is flagged requires_human_approval — pauses execution and creates an ApprovalModel. The orchestrator awaits an asyncio.Event that the approvals API sets on your decision; rejection fails the execution cleanly.

ToolPermissionExtra hardening
file_readerREAD20 KB default / 100 KB hard cap — raw content flows into the LLM context
file_writerWRITEcreates parent dirs; append mode explicit
python_executorWRITEsubprocess + timeout; output capped at 20 KB; network imports regex-blocked so it can't silently bypass the EXTERNAL_ACTION gate
calculatorREADAST-whitelist arithmetic only — no eval
http_requestEXTERNAL_ACTIONhttpx with timeout; approval gate before first call
web_searchEXTERNAL_ACTIONSerper / SerpApi / Brave auto-detected from env; without a key returns a config hint instead of failing
The python_executor gotcha (worth knowing): without the network-import block, an agent whose plan listed only python_executor could do import requests and reach the internet — silently skipping the human approval that web_search/http_request are forced through. The regex check turns that into an explicit error telling the agent to use the gated tools instead.

Model routing (Phase 9, already wired)

llm/router.py selects a tier per task: the intent's task type maps to a tier (qa/document/automation → fast, data_analysis/coding → default, research/business → reasoning), complexity keywords upgrade, and single-agent plans with only READ tools downgrade to fast. The planner additionally raises max_tokens for itself — reasoning models can burn most of their budget on hidden chain-of-thought before emitting the structured answer, and a truncated JSON plan is worse than a slow one. LiteLLM num_retries=3 absorbs transient Ollama Cloud 500s inside a single call.

Evaluation & replanning, precisely

The engine runs two passes. Structural: did every agent complete, did anything fail, is output non-empty — collecting issue strings. Criteria: each named criterion gets a heuristic score —

CriterionScored as
completenesscompleted agents ÷ total agents
accuracy1.0 if status=completed and zero failed agents; 0.5 if completed with failures; else 0
formatnon-empty outputs ÷ total outputs
relevance1.0 if any output exists (heuristic)
unknown (e.g. file_created)1.0 if execution completed, else 0

Scores average into the overall; success requires status == "completed" and score ≥ the plan's threshold. On failure the Replanner rebuilds an intent string that embeds the original intent, the failed agents and the issues, hands it back to the LLM planner, and the loop re-runs — bounded by max_replans = 2. An optional LLM-judge pass (use_llm=True) can score quality on top of the structural checks.

Skill system internals

A skill is a SkillSpec — id, name, description, version, inputs/outputs, agent IDs, tool IDs, workflow dict, evaluation criteria, permissions, tags. The registry stores skills plus versions (SkillVersionModel.spec_data JSON), with exactly one active version; activation flips is_active atomically, so rollback is just activating an old row. Usage metrics (usage_count, success_count, failure_count, avg_duration_seconds) update after every skill run. 

# Import pipeline (skills/import_export.py) — nothing executes before approval:
Upload .skill.zip → Extract → YAML validate → security scan
  → dependency check (tools exist?) → preview → user approves → install

# Reuse pipeline (routes_plans.py + yaml_parser.py):
discover_skills(intent)            # keyword match on name+description+tags
  → score > 0.5 → parse_agent_specs_from_yaml(spec_data)   # full AgentSpecs

Bug found & fixed while writing this guide: skill-reuse plans used to store the raw SkillSpec as plan_data — where agents is a list of string IDs — so PlanSpec(**plan_data) at execution time failed validation, and the frontend's PlanCard crashed rendering string agents. The reuse path now reconstructs full AgentSpecs from the skill YAML and validates the assembled PlanSpec before persisting, with LLM-planner fallback.

Observability: events and state

Every state change is an ExecutionEventModel row — type, agent_id, tool_id, status, duration_ms, error, timestamp, JSON data — persisted through events.py and also pushed to in-memory queues for SSE. The event timeline from the recorded demo run:

Execution state (state.py) persists current_nodes, completed_nodes, failed_nodes, outputs, tool-call and cost totals to the DB after every agent step — so a crash mid-workflow leaves a recoverable record rather than an orphaned run. Correlation IDs (task_id, execution_id, agent_id) thread through all log lines.

Design decisions worth knowing

  • Structured plans or nothing — the LLM planner runs with output_schema and a validator; free-form model output can never reach the orchestrator. (Trade-off: an output_schema agent can't also use tools, so the planner is deliberately tool-free.)
  • Reuse before generation — skill discovery runs before the LLM planner on every intent; regeneration is the fallback, not the default.
  • Planning ≠ execution — the planner cannot execute tools (it has none), and the orchestrator never improvises; separation is enforced by module boundaries, not convention.
  • Approvals as data — approval requests are DB rows + asyncio Events, so a paused workflow survives a server restart and can be resolved from any client.
  • Event-sourced-ish execution — state persists after every step; the UI is a projection of stored events, not of in-process memory.
  • Minimum agents — the planner prompt hard-codes "1 agent for simple tasks" and the demo proves it: CSV→Excel is one agent, not a committee.
  • Bounded autonomy everywhere — max_iterations/max_tool_calls/timeout per agent; max_replans/max_execution_time/max_total_tool_calls per workflow; retry ≤ 3 per agent. No path runs away.
  • Skills are files too — YAML in skills/builtin/ or zipped imports; the DB is just the versioned store. Export → import round-trips between environments.
