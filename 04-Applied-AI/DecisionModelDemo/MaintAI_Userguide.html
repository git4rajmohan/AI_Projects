🏭 MaintAI Decision Platform — From Machine Signals to Explainable Maintenance Decisions

Python · Streamlit · SQLite · Ollama: validated sensor readings feed a deterministic rules engine, then the local tev1:4b decision model scores the situation on a non-standard POST /v1/systemone endpoint, and a six-rung policy ladder turns evidence into one of four auditable outcomes — with a strictly grounded generative LLM that explains the already-made decision and can never override it. Eight Streamlit pages cover the full loop: fleet KPIs, sensor trends, a decision workbench, a versioned machine registry, CSV import with quarantine, a labelled-model evaluation harness with a confusion matrix, inspection history that closes the review loop, and a settings page with live connection checks. Every decision is persisted with its inputs, rule alerts, model probabilities, policy version and audit trail.

The 30-second pitch

Ask a generative LLM "should we stop this machine?" and two things go wrong: it answers in confident prose with no number attached, and it makes that call inside its own black box — no evidence trail, no reproducibility, no way to audit why. For maintenance you need the opposite: a decision you can measure, explain and defend.

MaintAI is that split, built properly. Sensor readings are validated (freshness, missing channels, plausibility) against per-machine limit versions, then a pure-Python rules engine evaluates warning/critical thresholds, rate-of-change alerts and trends — zero LLM in the loop. The local tev1:4b model classifies the situation into one of four actions (monitor / inspect / urgent_maintenance / insufficient_data) with probabilities and confidence. Then a deterministic six-rung policy ladder decides what actually happens: bad data routes to review before the model is even consulted, critical breaches override any monitor answer, a failed model call never becomes a safe decision, and low-confidence or self-contradicting output is escalated to a human. The model is evidence; the policy is the decision — they are never conflated. Only after the outcome exists does a generative LLM write an explanation, constrained to the supplied evidence by prompt rules, with a deterministic fallback when the LLM is down. Every run is persisted with its inputs, alerts, probabilities, policy version and an audit row — and a recorded inspection closes the loop on the dashboard.

The line that matters: rules and a decision model make the call, the LLM explains it, a human closes it — and nothing in that chain can quietly replace the rung above it.

The one-line principle

🧮 Deterministic first, model second

Thresholds, rate-of-change and trend checks are pure Python. A critical breach escalates to urgent review before the model's opinion is even requested — a safety hard rule beats any classifier. The model never gets the chance to talk a red machine back to green.

⚖️ The model is evidence, not the decision

Tev1's monitor at 90% sits in one panel; the policy outcome sits in a separate panel, computed by a fixed precedence ladder that can disagree. Invalid data, critical breaches, model failure, low confidence and monitor-vs-anomaly contradictions all route to human review regardless of what the model "wanted".

🧾 Explain, never authorize

The LLM explains the established outcome using only supplied evidence — it cannot invent readings, declare a failure, or override policy. Any LLM failure falls back to a deterministic explanation marked as a fallback. Every decision is persisted with an audit trail; a recorded inspection removes the machine from the live review count.

What is this project?

MaintAI is a maintenance decision-support demo for a fleet of machines. You feed it sensor readings (from CSV or its built-in synthetic generator); it checks them, applies engineering rules and asks a local decision model for a classification — then a fixed policy turns all of that into one clear outcome: keep monitoring, inspect, urgent maintenance, or "not enough data, review". A generative LLM writes the plain-language explanation of that outcome. A human inspects the machine and records what they found, which closes the case.

Using it is three moves:

  1. Watch — pick a machine on Machine Monitoring: latest values, configured limits, trend charts and decision history at a glance.
  2. Decide — run the analysis. The Decision Workbench shows validated input, rule alerts, the model's probabilities, and the separate policy decision — every number the pipeline actually produced.
  3. Close — on Maintenance History, record what the inspection found and mark it closed. The dashboard review count drops.

Think of it as a plant control room staffed by three specialists: a meter reader who insists on fresh, complete data; a rulebook engineer who escalates the moment a hard limit is crossed; and a storyteller who writes the report — but can only quote what the other two found, and can never change the decision. If the storyteller calls in sick, the meter reader's fallback report still ships.

The one rule that matters: everything here runs on synthetic data and demonstration thresholds. The app labels this on every screen. It does not control machinery, does not predict real failures, and never assumes a model's confidence means correctness. The value of the demo is the discipline: validate, rule-check, classify, decide by a fixed ladder, explain, audit, close.

What does working with it look like?

The app is a Streamlit multi-page app at http://localhost:8501 with eight pages. The sidebar shows both models and a live local-Ollama status pill; the home page links everything.

1

Seed — a fleet is born

python -m maintai.seed creates five machines, each a different story.

Every machine ships with its own limit version and one of five synthetic scenarios: BRG-001 degrades gradually, MIX-001 stays healthy, PMP-001 spikes over critical at the end of its window, MTR-001 drops readings, and CPR-001 throws a single sudden excursion. Same base operating point, five shapes of trouble — each is a different exercise for the pipeline.

Import — data earns its way in

Upload → preview → per-row validation report → confirm.

The Data Import page takes a CSV with seven required columns (machine_id, timestamp, temperature_c, vibration_mm_s, motor_load_percent, rpm, operating_hours). Every row is validated before insertion: bad timestamps, wrong machine ids, stale readings and missing channels are quarantined with a reason instead of silently dropped or silently accepted. Three bundled demo files (healthy → warning → critical) let you replay a machine's worsening day in order; run a decision after each import and watch the outcome move.

Decide — the ladder does the judging

Validate → rules → Tev1 → six-rung policy → persist… → explanation.

One click runs the whole pipeline. The Workbench then shows the two things the spec insists stay apart: left panel, Model output — the action, its probability bars, confidence and measured latency; right panel, Application decision — the policy outcome and whether human review is required, with the policy (limits) version used. 4

Explain — prose with a leash

The LLM gets the evidence, not the authority.

The explanation prompt supplies the validated readings, the configured limits, the trend lines, the rule alerts, the model line and the final policy outcome — and forbids the model from inventing measurements, declaring failures without evidence, overriding the decision, or following instructions hidden in inspection notes. Output is a strict JSON shape the app validates: a short summary, evidence bullets, recommended checks and limitations. If the LLM is unreachable, a deterministic fallback explanation is shown and labelled as such — the decision's record survives without prose.

5

Close — a human signs it off

Record the inspection; the loop closes on the dashboard.

On Maintenance History, an Engineer records findings, component condition, action taken and resolution status, tied to the specific decision id. A closed inspection removes the machine from the dashboard's live "requiring review" count — the KPI reflects reality, not stale alerts (the historical alert trend stays put for the record). A Viewer role can read everything but submit nothing — the demo role selector is the auth stand-in, and every write is audited with the acting role.

6

Measure — numbers, not vibes

Labelled batch → accuracy, review rate, per-class precision/recall, confusion matrix.

The Model Evaluation page generates 100+ deterministic labelled cases across the five machine types and pushes each through the real validation → rules → policy ladder with an injectable Tev1 stub — the same code the product runs, so the metrics measure the ladder, not a mock of it. Accuracy, human-review rate and unavailable rate headline the page; per-class precision/recall and a confusion matrix (expected × final action) show where the ladder and the model disagree. The banner repeats the standing rule: these are synthetic demonstration results, never production performance.

Architecture

Every concept owns one file. run_decision() composes them; every Streamlit page calls the same functions the pipeline uses — no page has its own private logic.

The policy ladder: why each rung exists

apply_policy() is the safety story of the app, written in 40 lines of pure Python. It is ordered so that nothing below a rung can override it:

  • Rung 1 — data first. If the reading failed validation, the model is never consulted. Reviewing bad data is a data problem, not a maintenance problem; labelling it data_review_required tells the human which kind of review to do.
  • Rung 2 — machine policy. A registry flag (mandatory_escalation) short-circuits everything; a machine that must always be escalated is.
  • Rung 3 — hard limits. Any critical breach forces urgent even if the model said monitor at 99%. Deterministic evidence beats model opinion — that precedence is the whole point of the app.
  • Rung 4 — failed model ≠ safe decision. A timeout or parse error becomes decision_unavailable_review_required, never "keep monitoring".
  • Rung 5 — soft evidence contradictions. Confidence below the threshold (default 0.70), an insufficient-data answer, or a monitor verdict while anomaly probability exceeds 0.5 route to review. Confidence is used only as a review signal — never as correctness.
  • Rung 6 — accept. Only a validated reading, no hard alerts and a coherent confident model answer produces an automatic decision — and even urgent_maintenance accepted here still requires review.

Model & LLM integration

🧠 Tev1 — the decision model

Served by local Ollama, called on the non-standard POST /v1/systemone endpoint — deliberately never /api/chat. The prompt poses three structured questions (choice maintenance action with the four allowed answers, anomaly present, severity score); the parser reads back typed shapes — {choice, probabilities{}, confidence} etc. — and fabricates nothing: absent fields stay None and the pipeline treats that honestly.

TEV1_MODEL, OLLAMA_HOST, TEV1_TIMEOUT_SECONDS (default 120).

💬 Generative LLM — the explanation voice

Any chat model over the shared LLM service: Ollama Cloud by default (LLM_MODEL + LLM_BASE_URL inherit the playground cloud config, so one OLLAMA_API_KEY serves both), or a local model by setting LLM_BASE_URL=http://localhost:11434. Swapping models is a one-line env change with zero code edits — and the key never appears in UI, logs, errors or exports, only in request headers.

Data, registry & audit

  • Append-only limit versions. Editing thresholds on the Machine Registry inserts a new version row — the old one stays. Every persisted decision records which limits version produced it, so any past decision can be reproduced as-of its decision time.
  • Import quarantine, not silent coercion. import_core.classify_rows() separates valid rows from quarantined ones with per-row reasons (unparseable timestamp, unknown machine, stale, missing channel) and in-file duplicates — the page confirms before anything is written.
  • Audit trail everywhere. Machine edits, limit-version changes, imports and inspections all append audit rows carrying the acting role, entity and JSON details — the import history and review-closure logic both read from it.
  • One SQLite file. DATABASE_URL (default maintai.db); tables live behind a repository layer the pages never bypass.

Evaluation harness

evaluation_service.py generates ≥100 deterministic labelled cases (labels come from the generator's parameters, never from model output) across the five machine types and five true conditions: normal → monitor, warning → inspect, critical → urgent, missing_data and ambiguous → insufficient_data. Ambiguous cases are deliberately low-confidence or self-contradicting to exercise rung 5. Each case runs through the real validate → rules → policy ladder with an injectable Tev1 callable, then scikit-learn scores it:

What gets scored

  • Accuracy across the four canonical actions
  • Human-review rate (how much workload the ladder generates)
  • Unavailable/invalid model rate
  • Per-class precision / recall
  • Confusion matrix: expected vs final action
  • Measured Tev1 latency

What it deliberately is not

  • Not production performance — cases and replies are generated
  • Not a benchmark of Tev1 specifically — the canned replies are part of the generator
  • The point is the ladder: does bad data route to review, do criticals escalate, does a failed model stay unsafe-to-silent

Design decisions & trade-offs

  • A six-rung ordered ladder instead of weighted scores — maintenance safety decisions should be explainable in one sentence ("critical breach → urgent, period"). Weighted scoring would be cleverer and less defensible.
  • Model output and policy outcome are separate columns, separate panels, separate concepts — the demo's core lesson. The LLM reads the outcome, never writes it; explanation failures can't corrupt decisions.
  • Append-only limit versions — trivial cost, and every historical decision remains reproducible with the exact limits it was made under. A real CMMS would build on the same shape.
  • Quarantine over rejection — bad rows ship back with reasons instead of blocking the 500 good ones, and never enter silently.
  • Deterministic fallback explanations — the demo must work with the LLM down; a labelled fallback keeps the record complete and honest about its origin.
  • Synthetic data labeled on every page — the app's credibility comes from never pretending: thresholds are demonstration values, evaluation is generated, and confidence is a review signal, not correctness.
  • Models as config, not code — Tev1 and the explanation LLM are both env-selected; swapping either is a .env edit and a restart.
