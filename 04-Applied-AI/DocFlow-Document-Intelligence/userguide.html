🧾 DocFlow — Invoice Approval Engine — AI Reads, Code Decides, Humans Own the Risk

FastAPI + Streamlit + SQLite + Ollama (mock/live): an invoice PDF goes in — even a pure image scan — and a deterministic pipeline reads it (OCR fallback), verifies every number against the vendor master and purchase orders, applies eight ordered approval rules, and routes only genuinely risky invoices to a human reviewer with the full evidence side-by-side. Every step lands in an append-only audit trail you can replay. The AI never decides anything financial.

The 30-second pitch

Companies receive thousands of invoices as PDFs and scans. Today a person opens each one, checks the vendor, matches it to a purchase order, recalculates the totals, and routes it for approval — slow, error-prone, and unauditable.

DocFlow does that entire job in seconds. An AI reads the document — even a pure image scan, via OCR — and extracts structured fields with per-field confidence scores. Deterministic Python then verifies everything: vendor exists and is active, arithmetic is recomputed from the lines, the PO exists and its quantities/prices match within tolerance, the invoice isn't a duplicate, dates are sane. A rules engine (R001–R008, first trigger wins) makes the approval call, and only genuinely risky invoices reach a human — with the original document, the extracted fields, every check result, and the exact rule that fired shown side-by-side. The extraction LLM can run live (Ollama, OpenAI-compatible) or in mock mode that replays ground truth, so the whole pipeline is demoable and testable offline.

The line that matters: the AI only reads, the code decides, the human owns risk — and the audit trail remembers everything.

The one-line principle

🤖 AI interprets

Reads ugly scans and different layouts, extracts structured JSON with a confidence score per field — and on image-only pages, falls back to Tesseract OCR. The AI never decides anything financial: no thresholds, no approvals, no fraud calls.

✅ Code verifies

Nine validation checks, two-way/three-way PO matching, tolerances, duplicates, vendor status — all pure deterministic Python. Same input, same verdict, every time. Math is recomputed in code; LLM arithmetic is never trusted.

🧍 Humans decide

Bank-account changes, duplicates, missing POs, low-confidence reads go to a reviewer with the evidence side-by-side — approve, reject, correct & resubmit, or request info. Never a black box.

What is DocFlow? (plain language)

Think of DocFlow as a super-careful accounts-payable assistant. You give it an invoice PDF. It reads the document (even a photo of a faxed invoice), checks the vendor is real and active, matches every line against the original purchase order, recalculates all the math itself, and then either:

✅ pays it automatically  ❌ blocks a duplicate or  🧍 asks a human to review

Every step is written down in a logbook, so months later you can still replay exactly why any invoice was paid or stopped. Reviewers only ever see the risky minority — safe small invoices never interrupt anyone.

Reviewer actions — what each button does

✅ Approve — evidence checks out → final status approved, exception closed.
❌ Reject — real mismatch or fraud → final rejected. Leaves the inbox.
❓ Request Info — parked at info_requested until the missing piece arrives.
✏️ Correct & Resubmit — fix a wrong field (e.g. misread total) → the system re-verifies everything from validation onward. Corrected fields get confidence 1.0; the rest keep their original scores.

Tips for best results

Do
  • Enter your reviewer name first — action buttons stay locked until the sidebar knows who you are
  • Read the reasons list — the banner's reasons[] is the exact logic chain that produced the decision
  • Use the line table — invoice vs PO per line is where mismatches are obvious
  • Open the Audit timeline expander — one event per stage, timestamped, replayable
Avoid
  • Don't expect the AI to make financial judgement calls — by design it can't; the policy engine decides
  • Don't re-upload a processed invoice expecting a fresh result — the duplicate guard blocks it (that's the point); delete the record first
  • Don't trust a "PASS" wall blindly — read the two or three checks that matter for your vendor
  • Don't correct a field to force an approval — corrections re-run the whole verification chain, so the numbers must actually add up

Frequently asked questions

Do I need to know AI or programming to use this?

No. Upload a PDF, read the banner, click a button. The interesting part — why the system decided what it did — is spelled out in reasons and evidence on the same page.

Is this a real payment system?

No — no money moves and the vendors/POs are seeded fixtures in SQLite. But the control flow (duplicate guard, tolerance checks, approval bands, audit trail) mirrors how real AP automation is built.

Why not let the AI decide everything?

Because a confident wrong answer on a ¥1M payment is expensive. LLMs are excellent readers and unreliable judges. DocFlow uses the LLM for perception only — every decision comes from ordered, deterministic rules an auditor can read in one sitting.

What if the AI misreads a field?

Every field carries a confidence score. Low-confidence critical fields force human review, and a reviewer can correct any field and resubmit — the pipeline re-verifies everything from validation onward. The AI's read is a suggestion with evidence, never the final word.

System overview

DocFlow is a three-process demo with one honest boundary: a FastAPI app owns all business logic and persistence, a Streamlit page is a thin requests client that could run on a different host, and SQLite holds the systems of record. The only AI component is extraction — an OpenAI-compatible LLM call (Ollama, live or mocked) that returns structured JSON with per-field confidence. Everything downstream is deterministic Python.

The state machine

Policy engine — priority order

Rules are evaluated in order; the first trigger wins as the decision, but every triggered rule is collected into reasons[] so the reviewer sees the complete picture:

RuleTriggerDecision
R001same vendor + invoice number already recordedREJECT (blocked pre-insert)
R002bank account ≠ vendor masterHUMAN_REVIEW (mandatory)
R003PO number not foundEXCEPTION
R004any FAIL / MISMATCH checkEXCEPTION
R005any critical field confidence < 0.6HUMAN_REVIEW
R006total > ¥1,000,000FINANCE_REVIEW
R007total ≥ ¥100,000MANAGER_REVIEW
R008everything green, < ¥100,000AUTO_APPROVE
Zero LLM imports — the policy engine is pure Python over the validation and match reports. Its PolicyDecision carries .decision, .rule_id and .reasons, and gets its own policy_decided audit event before the outcome status event, so the audit sequence reads received → extracted → validated → matched → policy_decided → outcome.

Validation & matching dimensions

9 validation checks (always emitted)

required_fields · vendor_exists · vendor_active · vendor_name_match · bank_account · arithmetic · currency · duplicate · date_sanity
Statuses: PASS / FAIL / WARN / HIGH_RISK / DUPLICATE / SKIP. Every check is emitted on every run (audit completeness — a missing check is itself suspicious). Arithmetic is recomputed in code; LLM-stated totals are never trusted.

Matching (two-way + three-way)

po_exists · po_vendor · line_mapping · quantity · unit_price · total · goods_receipt
AI only suggests the invoice→PO line mapping (line_matcher.py); code verifies quantities against tolerance and totals exactly. Three-way matching adds the goods receipt — invoiced more than physically arrived is a mismatch.

Design decisions worth stealing

Mock-first extraction. EXTRACTION_MODE=mock replays ground-truth JSON — all downstream phases are testable with zero LLM dependency; flip one env var for live Ollama.
Graceful OCR degradation. No Tesseract binary? Image-only pages read as poor → human review. Never a 500. _ocr_available() catches the missing-binary exception; standard install paths are probed when PATH lacks it.
Corrections re-enter from validation. A reviewer's field fix updates the stored extraction and re-runs validate→match→policy — corrected fields get confidence 1.0, others keep their scores (no confidence laundering).
Read-only audit reconstruction. build_audit_report() replays the story from audit_events alone — the UI's workflow strips are driven by the same events, so the visual state can never disagree with the database.
Duplicate guard pre-insert. Re-uploads are rejected by R001 before any row exists; the audit event lands on the original invoice — idempotency without orphan rows.
Delete-for-retest. DELETE /invoices/{id} cascades children (FK-safe order) and refuses seeded fixtures — demo loops without DB resets.

Running it

# 1. Environment (Python 3.12 venv at project root)
.venv\Scripts\activate

# 2. Tests (from project root, run as module so `app` imports resolve)
.venv\Scripts\python.exe -m pytest tests/ -q
#    → 101 passed, 1 skipped (the skipped one needs a live LLM)

# 3. Evaluation harness — 10 scenarios through the full pipeline
.venv\Scripts\python.exe -m evaluation.run_eval
#    → evaluation/report.md + results.json (accuracy, recall, false approvals, latency)

# 4. API (seed the DB first if data/docflow.db is missing)
.venv\Scripts\python.exe -c "import app.db; app.db.seed('data/docflow.db')"
.venv\Scripts\python.exe -m uvicorn app.api.main:app --port 8000

# 5. Reviewer UI (separate terminal)
.venv\Scripts\python.exe -m streamlit run ui/reviewer.py
#    → open http://localhost:8501 · set API base http://127.0.0.1:8000 · type your reviewer name
