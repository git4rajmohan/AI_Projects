Hospital Appointment Scheduler & Confirmation Bot — LangChain LCEL · FastAPI · Ollama Cloud · Twilio SMS

1. Overview

What It Is

A production-style scheduling service for a hospital (or any appointment-based business) that converts free-form natural language — an email, an SMS, or a web-chat message — into a structured, confirmed appointment. A patient can write "I need to see a dermatologist next Monday around 2pm, my number is +1-555-123-4567" and the system will:

  1. Understand the request via an LLM and turn it into typed, validated data (Pydantic)
  2. Check a business-rules calendar (weekdays, 09:00–17:00, no double-booking)
  3. If the exact slot is taken, automatically find the next free slot within 7 days
  4. Send the patient an SMS confirmation (real Twilio, or a deterministic mock in dev)
  5. Return a machine-readable ExecutionSummary JSON and record everything in SQLite

It ships with a single-file enterprise web console (chat + calendar + bookings + SMS audit trail) served directly by FastAPI — no Node, no build step.

2. How It Works

Processing Pipeline

One request flows through five deterministic stages. Every stage is independently logged and testable:

Step 1 — LLM Extraction

The system prompt instructs the model to be conservative: only extract what is explicitly stated, resolve relative dates ("next Monday") against the current date, default missing times to 09:00, and emit null for anything unknown. Output is constrained by PydanticOutputParser format instructions injected into the prompt — so malformed LLM output fails loudly at the parser boundary rather than corrupting downstream logic.

Step 2 — Intent Routing

IntentBehaviorStatus returned
schedule / rescheduleFull pipeline (calendar → SMS → booking)confirmed
cancelAcknowledged, no slot touchedcancelled
inquiryAnswered from extracted fields onlyconfirmed (informational)
Extraction failureShort-circuits; nothing is booked or senterror

Step 3 — Calendar Check

CalendarService applies hard business rules first (fast, no I/O), then consults two sources of "busy": an in-memory cache of pre-existing seed bookings loaded at startup, and the live bookings table (for bookings made since startup). When the requested slot is taken, find_next_available() probes hour-by-hour (rounded up) for up to 168 iterations — exactly 7 days — returning None if the whole window is full.

Step 4 — SMS Confirmation

SMSService has a strict mode hierarchy so development never requires Twilio:

  • skip — no phone in the request → SID SKIPPED_NO_PHONE
  • mock — TWILIO_ACCOUNT_SID == "mock" (default) → deterministic fake SID, no network
  • twilio — real creds → tries the trial-compliant template body "sms_appointment_reminders" first (Twilio trial accounts restrict message bodies to predefined template names); on failure falls back to the custom composed body (paid accounts)
  • error — any Twilio exception → recorded with mode='error'; a startup cleanup job deletes leftover error rows
Trial-account reality check: Twilio trial accounts can only send to verified destination numbers. A booking to an unverified number will produce a mode='error' SMS record (HTTP 422 from Twilio) — this is expected behavior, not a bug, and the row is auto-purged on next startup.

Conversational Chat Engine

The /api/chat endpoint runs a second, session-aware LLM loop on top of the same building blocks. Each session (keyed by session_id) keeps a ConversationState:

  • An incremental field-extraction prompt merges the user's latest message with everything already collected — so "next" or "make it 3pm instead" resolve correctly
  • Symptom → department inference is built into the extraction prompt (e.g., chest pain → cardiology, rash → dermatology)
  • Booking fires only when the required set is complete: patient_name + department + datetime + phone
  • Reschedule flow reuses the stored phone/department — it only needs the patient's name to look up the booking
  • On unavailability, the engine proposes up to 3 alternative slots from find_next_available()

Web Console

app/static/index.html is a dependency-free single file served at /. Design system:

  • Light theme tokens (gray surfaces + one brand blue), collapsible sidebar shell + top app bar with live health pill
  • Inline SVG sprite (16 Lucide-style icons via <use href="#i-…">) — zero emoji, zero icon libraries
  • Views: Chat (bubbles, booking detail cards, typing indicator, quick-action chips), Calendar (7×8 grid with 3px status rails), Bookings & SMS History (sticky-header tables, pill badges, masked phones with click-to-reveal)
  • Accessibility: :focus-visible rings, prefers-reduced-motion support; responsive at 1024 / 900 / 640 px (off-canvas sidebar)

Enums AppointmentIntent (schedule/reschedule/cancel/inquiry) and ExecutionStatus (confirmed/no_availability/cancelled/error) make invalid states unrepresentable — the router is a plain if/elif on enum members, not string matching.

LCEL Chain Design (app/chain.py)

def _build_chain():
    llm = ChatOpenAI(
        model=settings.ollama_model,          # openai/gpt-oss:120b
        api_key=settings.openai_api_key,      # dummy — proxy substitutes real key
        base_url=settings.openai_api_base,    # http://127.0.0.1:11435/v1
        temperature=0.1,                      # deterministic extraction
        max_tokens=1024,
    )
    parser = PydanticOutputParser(pydantic_object=ExtractedAppointment)
    prompt = ChatPromptTemplate.from_messages([...]).partial(
        format_instructions=parser.get_format_instructions()
    )
    return prompt | llm | parser, parser
  • Determinism — temperature=0.1: the same input yields the same extraction, critical for testing and auditing
  • Format enforcement — the parser's JSON schema is injected into the system prompt; the parser then validates/types the response. A malformed response raises inside the chain and is caught in the orchestrator → status=error, no partial bookings
  • No LangGraph — deliberately linear LCEL per the original spec; the chat engine layers state management on top without a graph runtime

Services Layer (app/services.py)

CalendarService

Rule engine + booking façade. check_availability() = weekend guard → business-hours guard → seed-slot cache → DB lookup. find_next_available() = 168-hour probe. Mutations: book_slot, reschedule_booking, cancel_booking.

SMSService

Strategy pattern across skip/mock/twilio/error. Twilio client is constructed once at startup (only in real mode) with graceful fallback to mock if the SDK import/init fails. Every outcome — including errors — is persisted via db.add_sms_record().

SQLite Persistence (app/database.py)

CREATE TABLE IF NOT EXISTS bookings (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    datetime TEXT NOT NULL,          -- ISO-8601, hour-truncated
    patient_name TEXT NOT NULL,
    department TEXT NOT NULL,
    contact_phone TEXT DEFAULT '',
    sms_sid TEXT DEFAULT '',
    booked_at TEXT NOT NULL,
    is_pre_existing INTEGER DEFAULT 0
);
CREATE TABLE IF NOT EXISTS sms_records (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sid TEXT NOT NULL, to_number TEXT DEFAULT '',
    body TEXT NOT NULL, mode TEXT DEFAULT 'mock',
    sent_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_bookings_datetime ON bookings(datetime);
CREATE INDEX IF NOT EXISTS idx_sms_sent_at ON sms_records(sent_at);
  • WAL journal mode (PRAGMA journal_mode=WAL) for safe concurrent reads during API serving
  • Self-seeding — 10 pre-existing bookings inserted on first run so the calendar grid is demo-ready
  • Self-healing — init_db() purges ERROR_ rows from failed Twilio sends at startup
  • Hour truncation — bookings are stored as YYYY-MM-DDTHH:00:00, making slot math exact and index-friendly

Ollama Cloud Proxy (ollama_cloud_proxy.py)

Ollama's cloud API speaks native Ollama format, but LangChain's ChatOpenAI speaks OpenAI format. The proxy is a small FastAPI app at http://127.0.0.1:11435/v1 that translates both directions:

DirectionTranslation
Request in/v1/chat/completions → /api/chat; strips the openai/ model prefix; converts OpenAI tool_calls → Ollama format; flattens array content blocks to plain strings
Response outOllama chunks → OpenAI-style JSON; upstream auth uses OLLAMA_API_KEY (Bearer)
Why a proxy? It decouples the app from provider quirks: the app code stays 100% OpenAI-format (portable to any provider), while the proxy owns all Ollama-specific translation. Swapping to real OpenAI, Azure OpenAI, or a paid Ollama endpoint is a one-line .env change.

7. Security Notes

  • Secrets — all credentials live in .env (gitignored); the repo contains only .env.example with placeholders. Verified: no .env, no .venv, no data/ in git history; secret-pattern scan of all committed content = zero matches
  • Git auth — pushes use Git Credential Manager's scoped OAuth token stored in Windows Credential Manager; tokens never touch the repo
  • PII handling — patient phone numbers are shown masked (+15xxxxxxxxx) in the UI with click-to-reveal; the SQLite DB stays local and is excluded from version control
  • CORS — wide-open (allow_origins=["*"]) for local development; tighten before any shared deployment
