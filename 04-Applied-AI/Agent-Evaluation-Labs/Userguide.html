📊 Evaluating AI Agents — Observability & Evaluation Labs

Arize Phoenix + an OpenAI-compatible LLM: a sales-data analyst agent whose every step is traced, whose every skill is graded by LLM judges and code checks, and whose prompt changes are compared A/B — all driven from one Streamlit dashboard.

The 30-second pitch

A raw LLM agent looks smart in a demo and fails silently in real use. Did it pick the right tool? Is the SQL it wrote even relevant to the question? Is the answer clear — or merely plausible? Did the change to a prompt quietly regress what used to work? Without instrumentation you are guessing; with it, you are doing evaluation-driven development.

This app builds a data-analyst agent (router + 3 tools, fully traced to Phoenix) and wraps it in four evaluation labs: a tracing demo to see every span, router & skill evals that judge real recorded tool calls, SQL, clarity and chart code, a convergence eval that scores path efficiency across 17 paraphrased questions, and an overall eval with 5 evaluators plus an A/B rerun against a modified SQL prompt. Each lab runs from the Streamlit dashboard with one click; scores, judge reasoning and failure evidence come back to the UI, with full traces in Phoenix.

The signal: evaluators observe the agent — they are not extra steps in its execution. Trace first, judge the recorded evidence, then iterate on the weakest component.

The one-liner variants

🔍 See everything

Every LLM call, tool call and SQL execution becomes a Phoenix span under an AgentRun root. The dashboard reconstructs span trees and inputs/outputs so you can confirm the path before you score it.

⚖️ Judge the evidence

LLM-as-judge grades recorded tool choices, SQL and answers in JSON mode; code evals execute generated chart code directly — no LLM involved. Judge reasoning, label and score are logged back to Phoenix as span annotations.

📈 Iterate with experiments

Datasets of questions are uploaded once and reused; experiments score agent runs reproducibly. Run the suite before and after a prompt change — regressions show up in the before/after score table, not in a user complaint later.

What is this app?

This is a teaching app for agent evaluation. It presents a sales-data analyst agent — an LLM that decides which tool to call (look up data, analyze it, generate a chart), and answers questions about a store-sales dataset — and lets you run four evaluation labs from a single dashboard. Each lab teaches a different way to measure an agent: its path, its individual skills, its answer, and its overall quality after a prompt change.

Think of it as hiring a smart analyst and watching their work instead of only reading the final report. The tracing (Phoenix) is the observer; the evaluators are the quality inspectors; the dashboard is where you press run and read the verdicts.

The journey of a question

Every question takes the same path through the agent. The labs differ only in what they do with the recorded path afterwards.

1

Pick a lab and press run

In the Streamlit dashboard, choose the lab from the dropdown and click Run evaluation. A status box streams the run live; runs take minutes because each agent turn involves real LLM calls.

2

The agent works

The router LLM picks tools, SQL is generated and executed locally on the sales data, analyses are written, chart code is produced. Nothing here is simulated.

3

Phoenix records it

Every call lands in Phoenix (project evaluating-agent) as spans: AgentRun → router_call → tool spans → nested LLM spans.

4

Evaluators judge

LLM judges read the recorded spans and reply with a JSON label + reasoning; code evals execute generated chart code directly. Scores are logged back to Phoenix as annotations.

5

You read the verdict

The dashboard shows answers, a per-check score table with a target of 1.00, judge reasoning for graded examples, and a link to the full traces.

Honest limits (shown in the app too): Lab 7 scores cover all matching stored spans, not just the latest run; convergence measures efficiency only and a short path does not prove a correct answer; Lab 11 treats missing SQL/chart tool responses as passing those checks — inspect tool selection as well.

How to use it

  1. Configure .env next to the code: OLLAMA_API_KEY, OLLAMA_BASE_URL, OLLAMA_MODEL, PHOENIX_ENDPOINT. No key, no agent — the app tells you exactly where to create one.
  2. Launch python -m streamlit run app.py → http://localhost:8501. Phoenix starts itself at http://localhost:6006 on first use.
  3. Pick a lab — the panel under the dropdown explains what it does, the expected output, and its limits before you spend any tokens.
  4. Read results — answers, score table, graded examples with judge reasoning; Open Phoenix results takes you to the raw traces and experiments.
Tip: run Lab 5 first. Seeing the span tree of a single question is the fastest way to understand what the other labs are judging.

Frequently asked questions

Why does a run take minutes?

Each agent turn means multiple real LLM calls (router, SQL, analysis, chart). Lab 7 runs 6 questions × 4 judges; Lab 9 runs 17 questions. The dashboard streams progress, and Phoenix receives traces as soon as spans finish.

Is "Run completed" the same as "everything passed"?

No — it only means the script exited cleanly. Always read the score table; the app says so explicitly next to the banner.

What does a convergence score of 1.00 mean?

This run's question took the shortest path observed across all 17 phrasings. It says nothing about whether the answer was right — that's what Lab 11's other evaluators are for.

Where are lab datasets and annotations stored?

Inside Phoenix. Datasets are created once and reused on every rerun (no duplicate stacking); judge scores are span annotations; experiments appear in Phoenix's Experiments view.

Can the judges be wrong?

Yes — LLM judges grade recorded evidence against prompt rails ("correct" vs "incorrect") and can mislabel, which is why every grade ships with its full reasoning for you to inspect. Code evals (runnable code, SQL result match) are deterministic.

System overview

Streamlit (app.py) is only a launcher and renderer: it runs python eval.py <lab> as a subprocess, streams stdout, and parses two conventions out of the log. All agent behaviour lives in utils.py; all evaluation logic lives in eval.py. Phoenix (local server, auto-started) stores traces, datasets, annotations and experiments.

The agent (utils.py)

  • Router loop — run_agent() loops: system prompt prepended once, chat.completions.create(tools=…); if the model returns tool calls they are executed and appended, otherwise the final content is returned. Each loop iteration is a router_call chain span; the whole run sits under an AgentRun agent span (start_main_span()).
  • Three tools — lookup_sales_data (LLM writes SQL → DuckDB over the parquet), analyze_sales_data (LLM interprets results), generate_visualization → extract_chart_config (JSON mode + Pydantic validation) → create_chart (LLM writes Python). All decorated @tracer.tool()/@tracer.chain().
  • The trajectory trick — run_agent returns only the final string but appends every message to messages in place. That list is the full path; process_messages() summarizes it into {tool_calls, tool_responses, final_output, path_length} matching tool responses by tool_call_id. Labs 9/11 evaluate this dict directly.
  • Swappable SQL prompt — update_sql_gen_prompt() mutates the module global; Lab 11's A/B rerun is literally one function call between experiments.

Shared judge plumbing (eval.py)

One stack, reused by every lab — written once:

  • run_judge() — LLM-as-judge via raw HTTP + JSON mode (response_format: json_object, fallback to plain chat), robust label parsing with rail fallback, per-call default labels chosen by callers. Wrapped in suppress_tracing() so judge calls never appear as spans.
  • judge_dataframe() — row-wise judging over span-query dataframes; maps label → 1/0 score on rail order.
  • log_span_evaluations() — uploads label/score/explanation back to Phoenix as span annotations (async), then emits a UI line.
  • get_or_create_dataset() — uploads a dataset once, reuses by prefix on reruns; no duplicate stacking.
  • print_ui_scores() — emits __EVAL_UI__ {json} lines: the dashboard's only machine-readable score channel.
  • run_experiment / evaluate_experiment — thin wrappers around PhoenixClient.experiments (timeout raised to 120 s; agent turns take 10–20 s each).

Failure semantics: judge errors fall back to caller-chosen defaults (e.g. clarity → unclear, tool calling → incorrect); a lab failing one evaluator logs the failure and continues. Lab 11's code evaluators return True when the tool in question was never called — read "missing response = pass" as a scope limit, not a success.

The dashboard's parsing contract (app.py)

The subprocess protocol keeps the dashboard generic — eval.py changes freely as long as it keeps speaking these two formats:

# 1. answers (Labs 3/5/7 questions echo through):
Q: What was the most popular product SKU?
A: **…answer markdown…**

# 2. machine-readable evaluation scores (anything with scores):
__EVAL_UI__{"title":"Overall Experiment","scores":[
  {"evaluator":"function_calling_eval","passed":7,"total":7,"score":1.0}]}
  • Answers → parse_output() regex → rendered as bordered question/answer cards.
  • __EVAL_UI__ lines → JSON rows → per-check table with evaluator descriptions, locations in the agent, pass/fail status and next actions.
  • Phoenix is queried back for display: Lab 5 span trees via SpanQuery; Lab 7 graded examples via raw GraphQL (spans + their annotations with judge reasoning).
  • st.session_state.run keyed on the selected lab, so switching labs shows "No current output" until you rerun.

Design decisions worth knowing

  • Raw HTTP judges instead of phoenix.evals — that API was removed in Phoenix 20.x; raw HTTP also guarantees judge calls stay un-instrumented (no judge spans leaking into the very traces being judged). suppress_tracing() is belt-and-braces.
  • Ollama Cloud realities — it rejects OpenAI structured-outputs and forced tool calls: chart config uses JSON mode + regex rescue + Pydantic fallback; the Lab 11 tool template uses .replace() not str.format (braces inside embedded JSON examples), plus an explicit "lookup_sales_data is always correct first" scope note so the judge doesn't over-flag routers.
  • Windows robustness — stdout/stderr forced to UTF-8 (Unicode from LLM output), matplotlib Agg backend so generated plt.show() never blocks, ANSI escapes stripped from subprocess output.
  • Datasets are immutable-once — questions and expected SQL results are baked into OVERALL_QUESTIONS; the expected sql_result strings define the digit-concatenation match for evaluate_sql_result.
  • Tracing registration happens at import time — importing utils starts Phoenix if needed (90 s readiness wait) and instruments OpenAI calls; every consumer lab inherits tracing for free.
