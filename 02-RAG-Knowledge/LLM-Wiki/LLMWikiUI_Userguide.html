📚 LLM Wiki UI — From a Pile of Documents to a Living Knowledge Base, Hands-Free

FastAPI + React + any LLM: drop source documents into Clippings/, press Run Ingest, and watch the model write a structured wiki — source pages, entity pages, concept pages, a master index — with Obsidian-style [[wiki-links]] stitching it all together. Then browse it as a folder tree or an interactive D3 link graph, and interrogate it in a streaming chat that cites its sources and grades its own confidence. No database — the wiki is plain .md files you can open in Obsidian, version with Git, and read with your own eyes.

The 30-second pitch

You have forty product documents in a folder. Someone asks "how does offline sync work?" and the answer is buried in three PDFs, a spreadsheet and a wiki nobody updated since last year. Reading, indexing and cross-referencing all of it is your problem — forever.

This project turns that pile of documents into a self-maintaining wiki. Drop the files into Clippings/, hit Run Ingest, and an LLM reads each one and writes structured wiki pages: a source page per document, entity pages for every component and feature it mentions, concept pages for the cross-cutting ideas, and a master index.md that catalogs everything. Pages are cross-linked with Obsidian [[wiki-links]], browsable as a folder tree or an interactive D3 force graph, and answerable in plain English — the Query tab retrieves the relevant pages, streams a cited answer, and shows a confidence score. It runs on any of 8 LLM providers (OpenAI, Azure, Anthropic, Ollama, LM Studio, Together, Baseten — or a GGUF model running locally on your CPU, no API key needed). The wiki is plain Markdown files: human-readable, Obsidian-compatible, Git-friendly.

The line that matters: documents go in one side, a cross-linked, queryable knowledge base comes out the other — and the LLM does all the writing.

The one-line principle

📥 Ingest → 🕸️ Browse → 💬 Query

Three stages, one loop. Ingest turns documents into linked wiki pages. Browse explores them as a tree or force-directed graph. Query answers questions from the wiki only, with citations and a confidence grade. Each pass makes the next one smarter.

🗂️ Plain files, no lock-in

Every page is a .md file with YAML frontmatter, stored in wiki/sources|entities|concepts|analyses. No database, no proprietary format — open it in Obsidian, grep it, or git diff it. Clippings/ is never modified; the wiki is fully regenerable.

🔍 Answers you can audit

Query answers stream token by token, then land with citation chips (click to open the exact page) and a confidence score. The system prompt forbids the model from using outside knowledge — if the wiki doesn't know, it says so.

What is this project?

LLM Wiki UI is a wiki that writes itself. You feed it documents; a large language model reads each one and produces a structured, cross-linked knowledge base — then answers questions about it, showing its sources and how confident it is.

In practice you do three things:

  1. Create a project — one folder = one wiki (one product, one domain)
  2. Drop documents in and run Ingest — the LLM writes source, entity and concept pages and links them together
  3. Browse or ask questions — tree/graph navigation, or a chat that answers from the wiki only

Think of it as hiring a librarian who never sleeps. Every time you hand her a new document she reads it, writes a summary card, files it under the right headings, updates the master index, and adds "see also" strings to every related card she has ever filed. When you ask a question she pulls the relevant cards, answers only from them, and tells you which cards she used — and how sure she is.

What does using it look like?

The app has three tabs. Here is the whole journey.

Step 1 — Configure the LLM once

In Config → LLM Connection pick a provider from the dropdown — OpenAI, Azure OpenAI, Anthropic, Ollama, LM Studio, Together AI, Baseten, or Local CPU Model (a GGUF file running on your own machine, no API key, no internet). Enter the model and key, hit Test Connection, and a green ✓ tells you you're ready. Settings persist in config.json; keys are masked in the UI and the file is git-ignored.

Step 2 — Create a wiki project

In Config → Ingest, choose New Wiki, type a name, browse for a parent folder, and click Create Wiki Structure. The app scaffolds the whole skeleton: 

MyWiki/
├── AGENTS.md          ← the schema the LLM must follow
├── Clippings/         ← your raw documents go here
├── raw/articles/ · raw/assets/
└── wiki/
    ├── index.md · overview.md · log.md
    └── sources/ · entities/ · concepts/ · analyses/

Already have a wiki folder on disk? Choose Existing Wiki, point at the folder, and it's registered and set active.

Step 3 — Run Ingest and watch it write

Drag files onto the drop zone (or drop them into Clippings/ and hit Reload), tick the ones you want, and press Ingest Selected. A progress bar tracks file-by-file progress while the LLM's raw output streams live into the log — you literally watch pages being written. Each file finishes with a ✓ file (N pages) line. Rebuild Entire Wiki re-processes everything from scratch; Stop halts after the current file.

Step 4 — Browse the wiki

The View Wiki tab opens on a two-pane Tree view: folder sidebar on the left (sources, entities, concepts, analyses), rendered Markdown on the right. Every [[wiki-link]] in a page is a clickable button that jumps straight to that page; a Back button and a Backlinks panel ("which pages point here?") make navigation feel like Obsidian. The sidebar even resizes — grab the divider and drag.

Step 5 — Explore the link graph

Flip the toggle to Graph and the whole wiki becomes a force-directed constellation: pages are nodes, [[wiki-links]] are edges, colours distinguish sources (blue), entities (green), concepts (amber), analyses (red). Drag nodes, zoom, hover for the path, click a node to open that page. A ⚙ settings drawer exposes live controls: search highlight, hide orphan nodes, per-type filters, node size, link thickness, label modes, arrows, and the physics sliders (repel, link distance, gravity).

Step 6 — Ask questions

The Query tab is a streaming chat. Type a question; the backend picks the most relevant wiki pages, hands them to the LLM as context, and streams the answer back. Under the answer you get:

  • Sources — chips for every wiki page used; click one to open it in the viewer
  • Confidence — High / Medium / Low / None with a percentage, colour-coded green → red
  • Save — turns the answer into a permanent analyses/<date>-<title>.md page that future queries can find

Two retrieval modes: Keyword (instant word-matching on the index) or Semantic (a first LLM pass reads the index and picks pages — slower, smarter). And a General LLM toggle switches the chat from "answer from my wiki" to "just talk to the model directly" — same box, no wiki context, useful for anything the wiki doesn't cover.

Why this matters: the wiki is plain files. You can edit any page by hand, commit it to Git, or open the folder in Obsidian — the app reads whatever is on disk next time. The LLM writes; you own the result.

The 4-step workflow

1

Prepare sources

Drop .md / .docx / .xlsx / .pdf / .pptx files into Clippings/ or the upload drop zone.

One topic per file works best; clean Markdown beats scraped HTML. Uploads land in the project's Clippings/ folder (10 MB per file), and the file list shows a done / pending badge per file by checking wiki/log.md. Hover a file row for a 🗑 button — removing a file also deletes its generated source page and refreshes the index.

2

Ingest

The LLM reads each file and writes a source page + entity pages + concept pages + the updated index.

Every ingest call includes the project's AGENTS.md schema and the current index.md, so naming conventions stay consistent as the wiki grows. The output is parsed page by page, normalized (paths slugified, bare filenames sorted into the right folder by frontmatter type), and written to disk. A log entry lands in wiki/log.md, and the index is auto-rebuilt as a safety net if the model forgot it.

The one rule that matters: a single source can touch 5–15 pages. That's the design, not a bug — entities and concepts are shared, so ingest #2 doesn't rewrite them, it links to them. Expect the wiki to grow non-linearly.
3

Browse

Tree view for reading, Graph view for seeing the shape of your knowledge.

Isolated nodes in the graph are pages nobody links to — either fresh ingests needing cross-references or candidates for deletion. The Health Check will tell you which.

4

Query & health-check

Ask questions with citations and confidence; run a lint to find broken links, orphans and gaps.

The Health Check runs two phases: an instant programmatic scan (broken [[links]], orphan pages, pages with no outbound links) followed by an LLM narrative that flags contradictions, stale claims, concept gaps, and — most usefully — suggests the next documents to go find.

Try it yourself: two terminals and a browser. The Technical Guide has the exact commands; from empty folder to first answer is about five minutes.

Tips for best results

Do
  • Start small — ingest 2–3 files, inspect the pages, then batch
  • One topic per file — a 20-topic mega-doc dilutes every page it touches
  • Use Temperature 0.2–0.4 for ingest; raise it only for general chat
  • Save good answers as analyses — they become first-class wiki pages
  • Run a Health Check every 5–10 sources to catch link rot early
Avoid
  • Don't Rebuild Entire Wiki casually — it overwrites all pages, and LLM output varies run to run
  • Don't expect magic from 2B-class local models on huge PDFs — they get compact prompts and truncated sources by design
  • Don't ingest images expecting OCR — visuals are ignored; keep the alt text
  • Don't mix unrelated products in one project — the graph and retrieval both degrade

Frequently asked questions

Do I need to know programming to use this?

No. Configure one dropdown, drop files in a box, press two buttons. The developer-facing parts (ports, API, config file) are only in the Technical Guide.

Where do my API keys live?

In config.json next to the app — masked as *** in the UI, never sent back to the browser unmasked, and git-ignored. Local CPU and Ollama need no key at all.

Can the app damage my documents?

No. Clippings/ and raw/ are read-only as far as the app is concerned. Everything it writes lives under wiki/, which is regenerable by rebuilding.

What if the local model produces nothing?

The app doesn't give up: it strips thinking-block artifacts, retries empty answers, caps the answer length, and — as a last resort — builds an extractive answer directly from the retrieved pages so you always get the relevant text even if the model flaked.

System overview

The project is a FastAPI backend + React SPA. Six routers (config, ingest, wiki, query, lint, utils) front five services (ingest, lint, LLM, local-model, wiki-manager). All long-running work — ingest, lint, query — is delivered as Server-Sent Events streams. Persistence is plain Markdown files + one config.json; there is no database anywhere.

The ingest contract: ===FILE:===

Ingestion is a single streaming LLM call per source file. The system prompt (in ingest_service.py) teaches the model a tiny file-emission protocol: 

===FILE: sources/agilepoint-nx-portal.md===
---
title: "AgilePoint NX Portal"
type: source
…
---
(page body with [[wiki-links]])

===FILE: entities/portal.md===
…
===FILE: index.md===
…

What happens to that raw text before it touches disk:

  • Thinking-strip — removes <|channel|>thought…<|channel|>response, <think> and <thinking> blocks that reasoning models emit
  • Path normalization — strips a leading wiki/, slugifies filenames, rejects invalid Windows chars, and collapses degenerate repetition loops small models fall into (email-email-email…)
  • Type-dir inference — a bare my-page.md with type: entity frontmatter is routed to entities/ automatically
  • log.md protection — the LLM can never overwrite the append-only log
  • Evidence append — source pages get an ## Extracted Source Text block (≤20k chars) so answers stay traceable
  • Index fallback — auto_rebuild_index() regenerates index.md from frontmatter if the model didn't emit one

Context per call = AGENTS.md + current index.md + the source text. Local CPU models get a compact variant: schema-only prompt, source truncated to 8k chars, no index/overview output.

How retrieval works

POST /api/query/ accepts mode (wiki | general) and retrieval_mode (keyword | semantic). In wiki mode:

StageCloud modelsLocal CPU models
Page selection keyword: tokenize question, score overlap vs index slugs, top 8 — or semantic: an LLM call reads the index and picks pages keyword only, top 3 (semantic needs a second LLM pass these models can't afford)
Context budget 40 000 chars, full pages, index + overview always included 12 000 chars; entity/concept pages reduced to question-relevant snippets, source pages kept full
History Full prior turns Last 2 turns only, and only if the question looks like a follow-up ("it", "that", "more"…)
Answer limits Model's configured max_tokens ≤512 tokens, 120 s timeout, retry-once on empty answers
Fallback — Extractive answer built from retrieved snippets (keyword confidence still reported)

The SSE stream, in order:

data: {"type": "confidence", "score": {...}, "source": "keyword"}   ← preliminary, sent first
data: {"type": "token", "token": "…"}                               ← full answer (cleaned) as one or more tokens
data: {"type": "confidence", "score": {...}, "source": "llm"}       ← parsed from ## Confidence: N
data: {"type": "citations", "pages": [{"path": "entities/x.md", "title": "X"}]}
data: {"type": "done"}

The system prompt hard-forbids answering from general knowledge: no answer in the wiki ⇒ the model must literally say "The wiki does not contain information about this topic." The UI strips the ## References and ## Confidence: lines from the visible bubble and re-renders them as chips and the confidence widget.

Graph view internals

GET /api/wiki/graph walks every .md under wiki/, regex-extracts [[slug]] targets, resolves each to a real path, and returns {nodes, edges} with a group per folder. The frontend (D3 v7) runs a force simulation whose parameters are all live:

GroupFolderColour
rootindex / overview / log (top level) light purple
sourceswiki/sources/ blue
entitieswiki/entities/ green
conceptswiki/concepts/ amber
analyseswiki/analyses/ red

The ⚙ panel edits filters (search dim-highlight, orphans/attachments toggles, per-group visibility), display (node size, link thickness, labels always/hover/never, arrows), and physics (repel −600…−20, link distance 20…300, gravity 0.01…0.5) — applied imperatively to the live simulation, no rebuild.

Health check: two phases

# Phase 1 — pure Python (lint_service.run_lint, instant)
slug_map = {page.stem → path}            # every [[target]] must resolve
inbound   = {slug → [linking pages]}     # orphans = no inbound
outbound  = count per page               # no_outbound = dead ends
→ events: {"programmatic": {broken_links, orphan_pages, no_outbound_pages}}

# Phase 2 — LLM sees every page's first 400 chars + phase-1 results
→ flags contradictions · stale claims · concept gaps
· missing cross-refs · data gaps · suggested new sources

Both phases stream over the same SSE channel the UI already uses for ingest, and every run appends ## [date] lint | N broken links, M orphans to wiki/log.md.

The local CPU model service

local_model_service.py ships a catalog of GGUF models (Gemma 2 2B, Llama 3.2 3B, Qwen 2.5 3B, Phi 3.5 Mini, Gemma 4 E2B — all Q4_K_M, ~1.7–2.2 GB), downloads them from Hugging Face on demand into models/, and serves them through llama-cpp-python — CPU only, chat-template aware (gemma / llama3 / chatml prompt styles). The provider id is local-cpu; the config form shows a dropdown of downloaded models and adapts the whole pipeline to it (compact prompts, 512-token answers, extractive fallbacks). Drop a .gguf into models/ and it appears in the dropdown. When packaged as an exe, models/ and config.json resolve next to the executable.

Design decisions worth knowing

  • Files, not a database — the wiki is the source of truth. Git gives history; Obsidian gives portability; a rebuild regenerates everything. State lives on disk or nowhere.
  • Schema lives in AGENTS.md, not code — entity/concept taxonomies are per-project and editable without touching Python. The ingest prompt embeds it every call.
  • ===FILE:=== over JSON — models follow "emit files with markers" far more reliably than nested JSON of page objects; the parser is forgiving by design (slugify, type-inference, loop-collapse).
  • Every stream is SSE — ingest, lint, and query share one transport, so the UI's live-token rendering is identical everywhere and an AbortController gives a real Stop button.
  • Defence in depth for small models — thinking-strip → empty-answer retry → token cap → timeout → extractive fallback → auto index rebuild. The wiki degrades gracefully instead of failing.
  • Path safety everywhere — every file op goes through a resolved-path guard against traversal; uploads and LLM-emitted paths alike are sanitized before touching disk.
  • Wiki mode vs General mode — one toggle flips the contract: grounded-with-citations versus plain chat. Same provider, same stream, different system prompt.
  • Masked keys — the backend returns *** for stored keys and restores the real one server-side; the browser never sees a key it didn't type.
