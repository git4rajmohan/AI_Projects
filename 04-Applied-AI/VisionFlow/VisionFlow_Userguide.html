🎥 VisionFlow — From Video Frames to Counted, Tracked Objects

Python · Streamlit · Ultralytics YOLO11 · OpenCV: an uploaded video streams through a YOLO detector, objects are followed across frames with persistent track IDs (ByteTrack or BoT-SORT), and the app counts them two honest ways — current (visible in this frame) and unique (distinct track IDs seen over the run). Everything lands in one result screen: the annotated video with boxes, labels and a live count HUD, two per-class count tables, bar and line charts, a download button, and a frame viewer that replays any processed frame with its exact per-frame detections from the .jsonl sidecar. All controls live in one sidebar — model, confidence, IoU, classes, frame skip, box-area and track-length filters, preview FPS, tracking on/off, and the one button that starts everything.

The 30-second pitch

Ask a person to "count the cars in this hour of traffic video" and two things go wrong: they get tired by frame 2,000, and they count the same car several times because it appears in many frames. The naive script fix — counting detections per frame and adding them up — is worse: a car crossing 40 frames becomes a fleet of 40. What you actually need is a counter that knows which detections belong to the same physical object.

VisionFlow is that counter, built properly. YOLO detects objects per frame; ByteTrack (or BoT-SORT) threads those detections into persistent track IDs across frames; and the count of interest is taken from distinct track IDs seen during the run, per class — detections are never summed per frame. A live side shows the current frame with boxes, labels (CAR #12 0.87) and a counts overlay; below it, the two tables keep the current and unique counts visibly separate, so nobody quotes the wrong number. Each frame's raw detections are written to a .jsonl sidecar next to the annotated video, which is exactly what the built-in frame viewer replays — every box, ID and confidence you saw live is auditable afterwards.

The line that matters: the detector finds things, the tracker gives them an identity, and the counter only believes the identity — never the raw per-frame detections.

The one-line principle

🆔 Count identities, not frames

Current objects = detections visible in this frame (good for "how busy is it right now"). Unique tracked objects = how many distinct track IDs the run has seen, per class. Two tables, side by side, so the useful number is never confused with the easy number.

🌊 Stream, never hoard

Frames flow one at a time from cv2.VideoCapture through detection, counting and annotation to the output writer. The whole video is never in RAM, so a long recording processes the same as a short one — the progress bar and live preview update as each frame completes.

🧾 Fail loudly, in plain words

Typed errors (VideoValidationError, ModelError, TrackerError, VideoWriteError) carry one-sentence human messages shown via st.error — a corrupt file, a GPU that ran out of memory, a missing CUDA build — while technical detail goes to the log only, never to a stack trace on screen.

The signal: nothing here is a monolith. Reader, detector, tracker, counter, annotator, writer and dashboard are each one small module with one job, composed by a single process_video() generator — and any component that only needs frame → detections is swappable without touching the rest. The architecture is the lesson; YOLO is an interchangeable part.

What is this project?

VisionFlow is a video analysis demo: you give it a recorded video, it finds the objects you care about (people, cars, trucks…), follows each one across frames with an ID, and counts them — both how many are visible in any given frame and how many distinct objects appeared overall. You get an annotated video back where every detection is boxed, labelled and given its track ID, plus tables and charts of the counts, and a frame viewer to inspect any moment closely.

Using it is three moves:

  1. Feed — upload a video in the sidebar. The app validates it and shows file name, resolution, FPS, frame count and duration before anything else happens.
  2. Run — pick the model, adjust the sliders, tick the classes you care about, and press Start Processing. The live frame, stats and count tables update while it runs.
  3. Review — watch or download the annotated video, read the count tables and charts, and step through any processed frame in the frame viewer with its exact detections.

Think of it as a traffic-analysis booth staffed by three specialists: a librarian who accepts only legitimate video files and catalogues their metadata; a spotter with eagle eyes who finds and names every object; and a tally clerk who refuses to double-count the same car and keeps two columns — what's visible now, and what's been seen all run. The tally clerk is the one whose numbers you quote; the annotated video is the proof.

The honest limits: track IDs are only stable within one run. If the tracker loses an object behind a truck and re-finds it, that one object may be counted as two — occlusion and low confidence are the known failure mode. Frame skipping makes the video process faster but makes both problems more likely. The app warns about this on-screen rather than pretending it can't happen.

What does working with it look like?

The app is a single-page Streamlit app at http://localhost:8501. Everything you configure lives in the sidebar; everything you watch lives in the main area. The Start Processing button stays disabled until a video is uploaded, the model is loaded and at least one class is ticked — so a half-finished setup can't start a doomed run.

The 6-step workflow

1

Set up — once

.venv → pip install -r requirements.txt → copy .env.example to .env.

Python 3.11+. On GPU machines, force the CUDA build of PyTorch (pip may claim the CPU wheel is already satisfied — it isn't what you want); optional ffmpeg on PATH upgrades the output video to browser-playable H.264. Without ffmpeg everything still works — the output just may not play inline.

2

Upload — the video earns its way in

Sidebar → Upload Video → metadata card appears.

Drop in a .mp4, .avi, .mov or .mkv. The reader validates it before anything else: file exists, extension recognised, video actually opens, frames readable, resolution and FPS present. A broken upload fails in one plain sentence — and stops the app right there so you never wait for a pipeline run that can't start.

3

Configure — the sidebar is the lab bench

Model · confidence · IoU · classes · frame skip · min box area · min track length · display FPS · tracking.

Model: YOLO11 nano/small/medium (or whatever MODEL_NAME you configured) — smaller is faster, bigger catches more. Confidence and IoU sliders set what counts as a detection and how boxes are deduplicated. Classes: tick what you count; unticked classes are filtered out entirely. Frame skip processes every N-th frame for speed (with a live warning that it can break track IDs); Min Box Area drops tiny boxes (distant signs misread as cars); Min Track Length filters 1–2 frame flicker IDs out of the unique counts; Display FPS only throttles the pretty preview, never the processing.

4

Run — press Start Processing

Progress bar · live frame · stats · both count tables.

While the run progresses you see the annotated frame at your chosen preview rate, a stats bar (frame index, video FPS, processing FPS, processed/total frames, elapsed), and the two count tables refreshing in place. Errors mid-run — a GPU memory hit, a failed write — appear as one readable sentence and the run stops cleanly; resources are released even when the browser tab walks away mid-run.

5

Review — quotes come from the unique table

Final stats · count tables · bar + line charts · annotated video · download.

After the run: the Analytics section shows the full counts table with a bar chart, and a line chart of current-object totals across the run. The unique column is the headline number — how many different objects moved through the video per class. The annotated video plays inline (with an honest warning if ffmpeg was missing) and always offers a download.

6

Audit — the frame viewer

Step or play through processed frames; each shows its exact detections.

The viewer reads frame images from the output video and detections from the .jsonl sidecar — the same record written during the run, not a re-inference. For any frame you get the image (Output frame 42 (source frame 84) when frame skip is active), this-frame current counts, and a table of every detection: class, track ID, confidence and box coordinates. Play steps at your Display FPS and stops itself at the last frame.

Architecture

Every concept owns one file. process_video() composes them as a generator; the Streamlit page (app.py) only wires UI to the same functions the pipeline uses — no page has its own private logic. Nothing holds the whole video in RAM: frames are streamed one at a time.

The processing pipeline

process_video(src, dst, detect_fn) is the whole product in one generator call. Each frame yields a FrameResult (annotated image, detections, current counts, unique counts, stats) that the UI renders live; the sidecar line for output frame N holds the detections plus the source frame index.

Frame-skip subtlety: skipped frames are neither processed nor written, and the output writer runs at fps / (frame_skip + 1) so the annotated video keeps its true real-world duration. Detection boxes carry the source frame index even when the output frame counter differs.

Counting discipline: current vs unique

Current objects

  • Detections of a class in this frame, period.
  • Meaningful with tracking off — it's the "how busy is this scene" number.
  • Drives the per-frame line chart of current totals across the run.
  • Computed by Counter.count_current — no state, nothing remembered.

Unique tracked objects

  • Length of the per-class set of track IDs accumulated over the run (TrackState).
  • Detections with track_id = None never add — an unidentified box can't inflate it.
  • Min Track Length filter: an ID must survive N processed frames to count — kills 1–2 frame flicker IDs.
  • Reset at the start and end of every run; never compare IDs across runs.
The known overcount: unique counts can exceed the true object total when the tracker loses an object (occlusion, low confidence) and re-acquires it with a new ID. This is ByteTrack/BoT-SORT under stress, and the app's warning on frame skip exists because skipping frames makes it worse. Line-crossing counting (count on crossing a virtual line, once per object) is the post-MVP fix and is deliberately not bolted on yet.

Model & tracking integration

🧠 ModelManager

Wraps Ultralytics YOLO. DEVICE=auto resolves CUDA-vs-CPU at load and fails fast with an actionable message if cuda is demanded of a CPU-only machine. Inference failures are caught twice: torch.cuda.OutOfMemoryError becomes "try a smaller model, CPU, or a higher frame skip", and anything else becomes a plain "Detection failed on this frame" — the stack stays in the log. Results convert to a small Detection dataclass: class id, name, confidence, box, optional track id.

MODEL_NAME, DEVICE, CONFIDENCE_THRESHOLD, IOU_THRESHOLD.

🏷️ UltralyticsTracker

Implements a two-method Tracker ABC: update(frame) and reset(). Behind it, Ultralytics runs ByteTrack or BoT-SORT with persist=True. Because process_video only needs frame → detections plus an optional reset, a new tracker (or a different detector) is a new subclass — nothing else in the pipeline knows or cares. Reset drops the model's predictor so Ultralytics builds fresh trackers next run.

TRACKER= bytetrack | botsort.

Data hygiene

  • Inputs are sandboxed: uploads save under data/input/; output paths are derived from the saved name, so nothing outside OUTPUT_DIR is ever written.
  • Nothing is auto-deleted: same-named uploads and outputs are overwritten in place; clear data/input/ and data/output/ manually when you're done.
  • Logs, not screens: every typed error shows one human sentence; the technical trace goes only to the log via the shared logging util.
  • Sidecar fidelity: the viewer's detections are the literal JSON lines written during the run — an audit log you can diff, not a re-run of the model.

⌨️ Tests & troubleshooting

# offline suite — no GPU, no model download, no internet
.\.venv\Scripts\python.exe -m pytest
  • "CUDA was requested but is not available": set DEVICE=cpu or auto.
  • "GPU ran out of memory": smaller model (yolo11n), DEVICE=cpu, or a higher frame skip.
  • "Could not open the video / missing resolution or FPS": the file is corrupt or encoded oddly — try a re-encode.
  • Video won't play inline: install ffmpeg on PATH; download always works.
  • Sidebar error naming the model: weights can't load — check the name/connection.

Design decisions & trade-offs

  • A stream, not a batch — process_video() is a generator yielding one FrameResult at a time; memory stays flat for any video length, and the UI can render live progress straight from the yield. An early browser close still releases reader, writer and tracker via the generator's finally.
  • Two count columns, visibly separate — current and unique sit in two tables so nobody quotes a per-frame sum as "how many cars went by". The app's core lesson, and it's one line of code apart (count_current vs update_unique).
  • Detections as the interchange format — one small dataclass from detector to filter to counter to annotator to sidecar; every stage is testable in isolation, and tests run offline with no model.
  • Sidecar as audit log — the frame viewer replays recorded detections rather than re-running YOLO, so what you inspect is exactly what happened during the run.
  • Typed errors with human sentences — validation, model, tracking and writing each have their own exception whose message is safe to show; the UI never greets the user with a stack trace.
  • Config in one frozen dataclass — config/settings.py is the only .env reader; the rest of the app reads get_settings() and stays honest.
  • Tracker swap = one subclass — the pipeline consumes frame → detections + optional reset, so ByteTrack today, a custom tracker tomorrow, zero pipeline edits.
