🛒 AI E-Commerce Assistant — User Guide

A conversational shopping assistant built with Google ADK multi-agent architecture. Browse a catalog, add items to your cart, provide your details, and get a complete order summary — all through natural chat.

Google ADK 4 Agents Ollama Cloud · gpt-oss:120b LiteLLM Python

💡 What Is This App?

This is an AI shopping assistant you talk to in plain English — like a helpful store employee inside a chat window. You can:

  • 🔎 Browse products — see what's available in Smartphones, Laptops, and Headphones with prices.
  • 🛍️ Add items to your cart — just say which product and how many.
  • 📦 Check out — give your name, email, mobile and shipping address.
  • 🧾 Get an order summary — a clean, Amazon-style recap of your complete order.
Good to know Behind the scenes this is not one big program — it is a team of 4 small AI agents, each an expert in one step of your shopping journey, working together. You just chat; they coordinate.

🔄 How It Works (Plain Language)

Think of it like visiting a store with four friendly staff members:

🧑‍💼 1. The Store Manager (Ecommerce Agent)

Greets you, notes down your name, email and mobile, then hands you to the right specialist depending on what you want to do.

🛒 2. The Catalog Expert (Catalog Agent)

Shows you products in 3 categories — Smartphones, Laptops, Headphones — with prices, and adds your picks to the cart.

🚚 3. The Checkout Expert (Checkout Agent)

Takes your shipping address so the order knows where to go.

🧾 4. The Bill Desk (Order Summary Agent)

Prints your final order summary — your details, items, quantity, price and address — just like Amazon or Flipkart.

🚀 How To Run The App (End-to-End)

What you need before starting

  • Python 3.9 or newer installed on your computer.
  • An Ollama Cloud account (ollama.com) with an API key — the "brain" (AI model) runs in Ollama's cloud.
  • Internet connection (the AI model is called over the internet).
1
Open a terminal in the project folder

Navigate to the project directory AI_ADK02 in Command Prompt / Terminal / PowerShell.

2
Create & activate a virtual environment

This keeps the app's dependencies separate from the rest of your machine.

# Windows
python -m venv .venv
.venv\Scripts\activate

# Mac / Linux
python3 -m venv .venv
source .venv/bin/activate
3
Install the dependencies 
pip install -r requirements.txt

This installs google-adk (the agent framework), litellm (model connectivity) and python-dotenv (reads your secret keys).

4
Add your API keys

Create a file named .env in the project root (same folder as requirements.txt) containing:

OLLAMA_API_KEY=your-ollama-cloud-key-here
SERPER_API_KEY=dummy-value
Important Get your Ollama key from ollama.com → Settings → API Keys. The SERPER_API_KEY line must exist (any value) — one of the agents reads it at startup even though it isn't used yet. Never share or commit the .env file.
5
Launch the app 
adk web

This starts a local web server. You will see something like "Uvicorn running on http://localhost:8000". Keep this terminal window open — closing it stops the app.

6
Open the chat UI in your browser

Go to http://localhost:8000 (or http://127.0.0.1:8000). On the left panel, select the agent: ecommerce_agent. A chat window opens.

7
Start chatting!

Follow the sample conversation below. When finished, press Ctrl + C in the terminal to stop the app.

Terminal alternativeNo browser? Run adk run ecommerce_agent instead — the same conversation happens right in the terminal.

⚠️ Current Limitations

  • The product catalog is fictional (built into the agent for demo purposes) — no real inventory.
  • No real payment is processed; checkout only collects a shipping address.
  • Order tracking is mentioned in conversation but not implemented yet.
  • Session data lives in memory — closing the app resets everything.

🏗️ Architecture Overview

The application is a hierarchical multi-agent system built with Google ADK (Agent Development Kit). A root orchestrator agent owns a chain of specialized sub-agents, connected by agent-to-agent delegation (each parent lists its child as a tool). All agents share one session state dictionary — this is how data flows across the whole workflow without any database.

Why the odd nesting? Sub-agents are declared bottom-up: checkout_agent imports order_summary_agent, catalog_agent imports checkout_agent, and the root imports catalog_agent. ADK discovers the tree from root_agent when it scans the project folder.

🔗 Shared Session State — The Data Bus

All four agents run inside one ADK session. Every tool receives a ToolContext whose state dict is persisted by ADK. State is the only mechanism that carries data across agent boundaries.

KeyWritten byConsumed byExample value
name, email, mobilesave_user_info() (root)order_summary_agent"Ravi", "ravi@example.com", "9876543210"
cartsave_cart() (catalog)debugging / future agents{category, product, quantity, price}
item, quantity, pricesave_cart() (catalog)order_summary_agent"Pixel 9", 1, "Rs.70,000"
shipping_addresssave_shipping_address() (checkout)order_summary_agent"12 MG Road, Bengaluru 560001"

Top-level duplicates of the cart keys are stored on purpose — ADK resolves {item}-style placeholders in an agent's instruction from top-level state keys, so the order_summary_agent's template renders automatically before the LLM sees it.

🛠️ How It Was Created — Code Walkthrough

1 · Root agent — greeting, identity collection, routing

ecommerce_agent/agent.py. A FunctionTool writes user identity into state; strict rules in the instruction enforce the guardrail "never route to checkout before save_user_info() has been called" and "never answer yourself — always delegate".

def save_user_info(tool_context: ToolContext, name: str, email: str, mobile: str):
    tool_context.state["name"]   = name
    tool_context.state["email"]  = email
    tool_context.state["mobile"] = mobile

root_agent = LlmAgent(
    name="ecommerce_agent",
    model=LiteLlm(model="openai/gpt-oss:120b", api_base="https://ollama.com/v1", ...),
    instruction="""Workflow:
      - Greet; collect name, email, mobile (one at a time)
      - Once ALL THREE known → call save_user_info()  [mandatory]
      - Route to exactly ONE sub-agent: catalog (purchase) / checkout / tracking
      Rules: NEVER answer yourself; NEVER route to checkout before save_user_info()""",
    tools=[save_user_info],
    sub_agents=[catalog_agent],
)

2 · Catalog agent — product browse + cart writing

catalog_agent/agent.py. The (fictional) catalog lives in the instruction prompt. When the user picks a product, the LLM must call save_cart() with the exact price string it showed the user, keeping displayed and stored prices consistent. It also writes both a nested cart dict and flattened top-level keys for the summary template:

def save_cart(tool_context: ToolContext, category: str, product: str,
             quantity: int, price: str):
    cart = {"category": category, "product": product,
            "quantity": quantity, "price": price}
    tool_context.state["cart"] = cart
    tool_context.state["item"]     = product   # flattened for {item} template
    tool_context.state["quantity"] = quantity
    tool_context.state["price"]    = price
    return {"status": "saved", "cart": cart}

3 · Checkout agent — address capture

checkout_agent/agent.py. A minimal LlmAgent: collect the shipping address, call save_shipping_address() to persist it, then offer to hand off to the order summary agent.

4 · Order summary agent — state → formatted receipt

order_summary_agent/agent.py. It has no tools and no sub-agents. Its instruction embeds ADK template variables that ADK substitutes from session state before inference, so the LLM simply renders the receipt. A rule forbids inventing data not present in state.

instruction = """
Use the following from the state object and generate an order summary
(amazon / flipkart style). Read ONLY from state; do NOT invent info.

{name} {email} {mobile}
{item} {quantity} {price} {shipping_address}
"""

5 · Model wiring — the Ollama Cloud gotcha

Every agent uses the same LiteLlm configuration, and the choice of the openai/ provider prefix (instead of Ollama's native ollama/) is deliberate:

  • Ollama Cloud exposes an OpenAI-compatible endpoint at https://ollama.com/v1 — used here with native function calling, which gpt-oss:120b handles correctly.
  • The native Ollama API forces format: json whenever tools are attached, which makes this model return empty content → JSONDecodeError in LiteLLM. Using the OpenAI-compatible surface avoids that entirely.
  • extra_headers={"Authorization": f"Bearer {key}"} satisfies Ollama Cloud's auth for both body and header paths.

6 · How a turn is processed (ADK mechanics)

  1. adk web receives the user message and starts a Runner over the session.
  2. Active agent's instruction + template-substituted state + conversation history → LiteLLM → Ollama Cloud.
  3. LLM returns either text or a function call; ADK executes the Python tool, commits tool_context.state writes, and feeds the result back for the next model turn.
  4. For delegation, ADK transfers control to the sub-agent (an AgentTool), which repeats steps 2–3 within the same session.
  5. Every step is emitted as a session event — visible in the dev UI's event/state inspector.

🧭 Known Gaps & Extension Ideas

  • tracking_agent is referenced but not implemented — the root instruction lists it as a routing target, yet no module exists. Create tracking_agent/ mirroring checkout_agent/ and add it to the root's sub_agents.
  • Single item cart — save_cart() overwrites; make cart a list to support multi-item orders.
  • No persistence — swap ADK's in-memory session service for DatabaseSessionService (SQLite) to survive restarts.
  • Hardcoded model config — extract model/api_base/api_key into a shared helper reading .env to avoid repeating it in 4 files.
  • SERPER_API_KEY is loaded in catalog_agent but unused — wire a real web-search tool for live product lookup, or remove it.
  • Evaluation — add adk eval test datasets to automate the checklist above.
