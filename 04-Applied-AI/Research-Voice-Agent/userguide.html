🎙 Research Voice Agent — From a One-Line Prompt to a Finished Podcast, Hands-Free

FastAPI + Google ADK + Ollama Cloud: give it a prompt, a meeting transcript or an audio recording, and a small team of AI agents does the rest — a producer agent that researches or reads and writes the report, a podcaster agent that turns it into a conversational script, and edge-tts neural voices that speak it into an MP3. Everything streams live into the browser: a 10-step progress tracker, a log of every tool call, and an audio player the moment the episode is ready. One page, three modes, zero cloud lock-in.

The 30-second pitch

Producing a podcast episode the traditional way means research tabs, a notes doc, a script draft, an audio editor and a microphone. Ask a chatbot to "make me a podcast about AI news" and you get text — you still have to research, structure, script and record everything yourself.

This project collapses that whole production pipeline into one Start button. You pick one of three modes — AI News (researches fresh AI news for NASDAQ-listed US companies and enriches it with live stock data), Meeting Recap (turns a pasted transcript into a decisions/action-items recap), or Audio Summary (uploads a recording and transcribes it locally). A producer agent built on Google's Agent Development Kit plans the run and calls real tools — web search restricted to a domain whitelist, live tickers via yfinance, and a markdown writer. A second podcaster agent converts the result into a Joe-and-Jane style conversational script, and edge-tts neural voices synthesize the actual MP3 — in any of 12 languages, with 1–4 configurable hosts. The whole run streams into the browser: numbered step pills light up, a live log shows every tool call, and the report and audio player populate the moment artifacts are saved. All reasoning runs on one open-weights model (gpt-oss:120b via Ollama Cloud) — the orchestration is the product.

The line that matters: you press Start once; a research agent gathers, a podcaster agent voices, and the browser watches it happen live.

The one-line principle

🧭 Agents plan, tools act

The producer agent doesn't write the news — it orchestrates: it acknowledges, then silently calls web_search, get_financial_context and save_news_to_markdown before saying another word. Real work happens in tools, not in the model's imagination.

🎛 Presets over prompts

Five topic presets swap the prompt prefill, the domain whitelist, the search region, the agent's name and the step labels. "AI + market news" and "Entertainment — India" are the same engine wearing different scope rules — configuration, not code.

📺 Progress you can trust

The stepper pills are driven by ADK tool callbacks — the UI lights up when the agent actually calls a tool, not when it claims to. The live log, the agent banner and the artifact panels always mirror the real state of the run.

What is this project?

The Research Voice Agent is a web app that runs entirely on your own machine and produces finished content — written reports and spoken podcast episodes — from three kinds of input.

You give it one of three things:

  1. A prompt — e.g. "Research the latest AI news for NASDAQ-listed US companies". It searches whitelisted news sites, enriches stories with live stock prices, writes a structured report, then records a podcast with your configured hosts. news mode
  2. A meeting transcript — pasted text or a file. It extracts decisions, discussion, action items and open questions into a recap document, plus a highlights podcast. recap mode
  3. An audio recording — e.g. a recorded meeting. It transcribes the audio locally on your machine (nothing leaves it except the final summary request) and writes a clean summary with key highlights and action items. audio summary

Think of it as a tiny radio station with two employees. The producer does the journalism — researching, verifying, writing. The sound engineer takes the finished script and records it with professional voices. You are the station manager: you choose the show, press Start, and watch both employees work through the studio's glass wall — every step lit up on the board.

What does a run look like?

Everything happens on one page. You pick a tab, give your input, tune the settings if you like, and press ▶ Start. From then on the page is live:

  • A stepper — one numbered pill per workflow step (10 for news, 9 for recap, 4 for audio summary). Grey = waiting, pulsing amber = running, green = done, red = failed.
  • A now-working banner — which agent is on stage: the Research Agent, the Recap Agent, the Voice Agent, or the Transcription Engine.
  • A live log — every tool call, every saved file, transcription progress percentages — the same events the agents trigger, streamed as text.
  • Result panels — the report renders as markdown in the Report panel; the podcast appears in the audio player the moment the MP3 is written, with Download buttons under both.
  • Run history — the last runs with time, prompt and which artifacts were produced.
Only two messages come from the agent itself: a short acknowledgment right after you press Start ("Okay, I'll start researching…") and a final confirmation when everything is done. All the actual work happens silently in between — that's by design, so you watch the steps rather than read a wall of chatter.

A news run, step by step

The default 📰 AI News mode walks a 10-step workflow. The pills in the app light up in exactly this order:

1

Acknowledge

The producer agent confirms: "Okay, I'll start researching the latest AI news for NASDAQ-listed US companies…"

2

Search news

It calls web_search — but it never chooses sites freely: a callback restricts results to your whitelisted domains and forces a freshness window (last week by default).

3–4

Extract tickers & fetch financials

Companies are identified from the stories, then get_financial_context pulls live stock context via yfinance. Missing data becomes "Not Available" — the run never halts for it.

5–6

Structure & format the report

Findings are organized into the report schema — including a "Data Sourcing Notes" section that records exactly which search results were filtered and why.

7

Save the report

save_news_to_markdown writes ai_research_report.md — the Report panel updates the moment the file lands.

8

Write the script

The producer converts the report into a conversational script with exact speaker labels — Joe: … / Jane: … — matching your configured host names, count and personas.

9

Generate audio

The producer hands the script to the podcaster agent (a sub-agent), which calls generate_podcast_audio — edge-tts renders each host's lines with its own neural voice and the MP3 chunks are stitched into one episode.

10

Confirm done

The final message: "All done. I've compiled the research report, saved it to ai_research_report.md, and generated the podcast audio file for you."

The other two runs

🎙 Meeting Recap (9 steps)

The same skeleton with the input swapped: instead of searching the web, the producer reads your transcript (paste it or load a .txt/.md/.vtt/.srt/.docx file), then produces a recap document — Key Decisions, Discussion Summary, an Action Items table with owners and deadlines, Open Questions — and a highlights podcast saved as meeting_recap.md + meeting_recap.mp3.

Faithfulness rule: only what's actually in the transcript. No invented quotes, no invented decisions — missing details become "Not specified".

🎵 Audio Summary (4 steps, text only)

Upload an mp3/wav/m4a/… recording. A dedicated transcription engine (faster-whisper) runs locally in an isolated subprocess — you watch the progress percentage climb in the live log. One LLM pass then writes audio_summary.md with an Overview, Key Highlights (with timestamps), Action Items and Open Questions.

This mode deliberately produces no podcast — it's for reading the record, not re-broadcasting it. The raw transcript is kept as transcript_*.txt.

Quick start

  1. Put your Ollama cloud key in the .env file: OLLAMA_API_KEY=…
  2. Start the app: .venv\Scripts\python.exe podcast_ui.py
  3. Open http://127.0.0.1:8000 in your browser.
  4. Pick a tab, give an input, press ▶ Start.
First run is slower — once. The transcription model downloads one time (~a minute) and is pre-warmed automatically at server startup; every later run reuses it.

Tips for best results

Do
  • Pick the language before starting — the report, script and voices all follow the setting captured at Start
  • Keep the domain whitelist tight — fewer, better sources beat a giant list; the callback filters everything through it
  • Use "week" freshness — news mode is tuned for the last 7 days by default and that's where it shines
  • Watch the log, not just the pills — it shows which domains were filtered and what the tools actually returned
  • Preview hosts before a long run — Preview host N speaks a sample instantly
Avoid
  • Don't expect a podcast from Audio Summary — that mode is deliberately text-only
  • Don't start a second run while one is active — the server refuses with "a run is already in progress"
  • Don't expect real-time market prices — yfinance gives context, not trading data; missing tickers degrade to "Not Available" by design
  • Don't paste URLs outside the whitelist and expect them to be read — search is fenced to your domains on purpose

Frequently asked questions

Do I need to know AI or programming to use this?

No. You type what you want researched (or paste a transcript, or pick a file) and press Start. The interesting part — which tools fired, what was filtered, what the agents said — is all visible on the page, so you learn how it works just by watching.

Does my audio or my transcripts leave my computer?

Audio never does: transcription runs locally with faster-whisper. Only the final text of a summary, report or script request goes to the cloud LLM (Ollama Cloud) — and web search queries go to DuckDuckGo, restricted to your whitelisted domains.

Why "only two user-facing messages" from the agent?

Focus, again. The producer's instruction mandates an acknowledgment, silent work, and one final confirmation. That keeps the chat panel clean and makes the stepper the real narrative of the run — you watch progress instead of reading commentary.

What stops the research agent from making things up?

Three guardrails: search results only come from the whitelisted domains (enforced by a callback, not by trust); every stock lookup goes through the yfinance tool rather than the model's memory; and the report must carry a "Data Sourcing Notes" section listing what was filtered. Missing facts become "Not Available" placeholders — never invented numbers.

Can I use my own topic instead of the presets?

Yes — the Custom preset gives you a free prompt plus your own whitelist. Financial steps are skipped automatically for non-market topics, and the stepper relabels itself to match.

System overview

The project is a two-file application plus a subprocess: podcast_ui.py is a FastAPI + uvicorn server on 127.0.0.1:8000 that serves the single-page UI, owns run orchestration and persists settings to config.json. It imports lesson6_podcast_agent.py as the agent engine: a Google ADK Runner driving a producer Agent (tools: search, financials, markdown save) with a podcaster Agent exposed through AgentTool. An embedded OpenAI↔Ollama proxy (FastAPI on 127.0.0.1:11435) starts inside the same process so every LLM call can reach Ollama Cloud. Audio uploads bypass the agent loop entirely and go through a subprocess transcriber with a hard timeout. Shared state is one lock-guarded dict polled by the browser every 1.5 s.

The two agents, in code

The engine defines two ADK agents. The producer is rebuilt per run by podcast_ui.build_agents() — its instruction is assembled from the active topic preset (goal line, scope limitation, acknowledgment sentence, financial-steps variant) plus a hosts directive that encodes the configured host names, personas and the exact Name: text script format. The podcaster is a specialist with a single tool; the producer reaches it through AgentTool, which makes a sub-agent callable like a function. 

# lesson6_podcast_agent.py — the podcaster specialist
podcaster_agent = Agent(
    name="podcaster_agent",
    model=LiteLlm(model=OLLAMA_MODEL),        # openai/gpt-oss:120b
    instruction=_PODCASTER_INSTRUCTION,       # "call generate_podcast_audio with the script"
    tools=[generate_podcast_audio],
)

# the producer — preset-driven, four tools, callbacks for guardrails
root_agent = Agent(
    name="ai_news_researcher",
    model=LiteLlm(model=OLLAMA_MODEL),
    instruction=root_instruction(...),        # goal + scope + ack + hosts directive
    tools=[
        web_search,               # ddgs, whitelisted + freshness-enforced
        get_financial_context,    # yfinance tickers -> stock context
        save_news_to_markdown,    # report / recap -> artifacts/<mode>/
        AgentTool(agent=podcaster_agent),   # sub-agent as a callable tool
    ],
    before_tool_callback=[filter_news_sources_callback, enforce_data_freshness_callback],
    after_tool_callback=[inject_process_log_after_search],
)
Why no output_schema? The original lesson notebook set output_schema=AINewsReport on the producer. ADK disables tool use when an output schema is set — fatal for a workflow that lives on tool calls. The Pydantic schemas (AINewsReport, MeetingRecap, ActionItem, NewsStory) are kept as structure guidance in the instructions instead.

# generate_podcast_audio — the async-inside-async gotcha, solved
async def _synthesize() -> bytes:
    chunks = []
    for voice, text in segments:            # (voice, text) per speaker line
        tts = edge_tts.Communicate(text=text, voice=voice)
        async for chunk in tts.stream():
            if chunk["type"] == "audio":
                buf.extend(chunk["data"])   # raw mp3 bytes per host
        chunks.append(bytes(buf))
    return b"".join(chunks)

# ADK tool calls already run inside an event loop — asyncio.run() here
# would raise. So the synthesis runs on a thread with its own loop:
with ThreadPoolExecutor(max_workers=1) as pool:
    audio_data = pool.submit(lambda: asyncio.run(_synthesize())).result()
Script → voices: the tool regex-parses every Speaker: line, looks the speaker up in the configured host map, and synthesizes one MP3 segment per line with that host's edge-tts voice. Unrecognized speakers are skipped; no speaker lines at all returns a structured error telling the model the exact expected format.

Guardrails: what the callbacks enforce

The producer's tools are wrapped by ADK callbacks — the same mechanism that powers the stepper. Three of them are guardrails, so the model cannot bypass them even if it wanted to:

Callback (when)Enforcement
filter_news_sources_callback
before every tool		 Rewrites web_search queries to respect the whitelist; any result from a non-whitelisted domain is dropped before the model sees it.
enforce_data_freshness_callback
before every tool		 Forces timelimit='w' (the configured freshness window) onto every search so stale content can't slip in.
inject_process_log_after_search
after web_search		 Attaches the filtering log to the tool result — which is why every report carries a "Data Sourcing Notes" section the user can audit.
ui_step_tracker_before / _after
in podcast_ui.py		 Map tool names to workflow steps and light up the stepper pills — including multi-step jumps (a successful save marks formatting steps done too).

Audio-summary path — no agents involved

The upload is stored as recordings/recording_<ts>_<name>, then a worker thread runs a deterministic four-step script: spawn the transcriber subprocess, save transcripts/transcript_<ts>.txt, make one LLM call through the proxy (the summary prompt), and write artifacts/summaries/audio_summary.md. 

# _transcribe_sub.py — standalone process, streams JSON lines
{"p": 12.5, "m": "transcribing 01:23/11:05"}   # progress → live log
{"p": 100.0, "m": "done"}
{"final": true, "result": {...}}                # transcript + segments

# podcast_ui.py side
TRANSCRIBE_SUBPROCESS_TIMEOUT_S = 900          # hard cap; proc.kill() on breach
proc = subprocess.Popen([sys.executable, "_transcribe_sub.py", str(audio_path),
                         whisper_model], stdout=subprocess.PIPE, ...)
Why a subprocess? faster-whisper (ctranslate2) proved unreliable inside the uvicorn app process on Windows. A clean python.exe subprocess is robust, streams progress as JSON lines, and a hard 900 s timeout (plus the Stop button) kills it without taking the server down. The model is pre-warmed in a background thread at startup so the first real transcription isn't the cold one.

Design decisions worth knowing

  • One model, many roles — gpt-oss:120b plays researcher, writer, scriptwriter and audio specialist. Specialization comes from instructions and tools, not fine-tunes.
  • Sub-agent as a tool, not a hand-off — the producer calls the podcaster via AgentTool, so audio generation is just another step in one workflow rather than a conversation the user has to steer.
  • Embedded proxy over a separate terminal — the OpenAI↔Ollama translator is a FastAPI app started in a daemon thread inside the engine (after a /health check), so there's no second process to launch or forget.
  • Thread-per-run with a single-flight lock — one run at a time; shared STATE is lock-guarded; a stale "running" state with a dead worker self-heals on the next run.
  • Callbacks as the single source of UI truth — stepper pills advance on ADK tool events, never on string-matching outputs, so the UI can't lie about progress.
  • Async-in-async containment — edge-tts synthesis runs on a dedicated thread with its own event loop (and whisper in a subprocess), keeping ADK's running loop untouched.
  • Mode-routed artifacts — every artifact filename is resolved through output_path(filename, mode) into artifacts/news|recap|summaries, with _old_ archiving so panels never show stale content.
  • Graceful degradation — missing tickers become "Not Available", missing recap fields "Not specified"; the run always delivers its artifacts rather than dying mid-flight.

Troubleshooting

  • Page won't open — the server isn't running: start it with .venv\Scripts\python.exe podcast_ui.py and open http://127.0.0.1:8000.
  • "A run is already in progress" while idle — stale state; the server self-heals on the next run, or restart the server.
  • Port 8000 / 11435 busy — close stray python.exe processes from previous launches (on Windows each start spawns a launcher + interpreter pair).
  • First transcription is slow — the whisper model downloads once; later runs are much faster (and the startup pre-warm helps).
  • Wrong output language — set Report & podcast language in Configuration before the run; hosts 1–2 remap automatically.
  • Search returns little — check the whitelist domains and the freshness setting (week is a good default).

AgentAI AgentAn LLM given a role (instructions), capabilities (tools) and colleagues so it can act toward a goal instead of just completing text.The producer agent and the podcaster agent in lesson6_podcast_agent.py.

🛠️ Tools & callbacks

TermExpansionWhat It MeansWhere in This Project
Function ToolFunctionTool (ADK)A plain Python function the LLM may call by name; ADK exposes its signature as a tool schema.web_search, get_financial_context, save_news_to_markdown, read_transcript_file, generate_podcast_audio.
ToolContextTool Context (ADK)The handle a tool receives to reach session facilities and per-run settings.Parameter of generate_podcast_audio; carries the mode's audio basename.
CallbackTool Callback (before/after)ADK hooks that run around every tool call — able to inspect, rewrite arguments, or modify results.before_tool_callback / after_tool_callback on the producer; the UI's step trackers.
Whitelist FilterDomain WhitelistA fixed list of domains a search may draw from; everything else is dropped.filter_news_sources_callback + the per-preset whitelist_domains in config.json.
Freshness EnforcementData Freshness WindowForcing search results to a recency window (day/week/month/year) regardless of what the model asks for.enforce_data_freshness_callback — injects timelimit='w'.
Process LogData Sourcing NotesA machine-generated list of what the filters did, attached to search results and printed in every report.inject_process_log_after_search → the report's "## Data Sourcing Notes" section.
Structured SchemaPydantic ModelA class describing required fields so LLM output has a predictable shape.AINewsReport, MeetingRecap, ActionItem, NewsStory — used as instruction guidance (see note below).
Schema vs tools: setting output_schema on an ADK agent disables tool use entirely — so the schemas here guide the instructions instead of being enforced by the framework. That trade-off is documented in the Technical Guide's agent section.
