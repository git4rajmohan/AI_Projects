📚 RAG Documentation Assistant — From Raw Markdown to a Cited, Hallucination-Proof Answer

Python · LangGraph · ChromaDB · Ollama Cloud: an end-to-end Retrieval-Augmented Generation pipeline — three chunking strategies (character, structural/hybrid, embedding-semantic), nomic-embed-text embeddings in a persistent ChromaDB store, hybrid retrieval that fuses BM25 keyword scores with vector similarity via Reciprocal Rank Fusion, and a strictly grounded generator that cites [Source: doc, Section] on every claim — or refuses. Wrapped in a FastAPI visualizer that shows every step, every ranked list and every regression gate diff. Evaluation is two-phase: a 19-question frozen golden set scored with deterministic LLM-free metrics, plus optional Ragas LLM-judged scoring.

The 30-second pitch

Ask an LLM a question about your documentation and two things go wrong: it has never read your docs, and when it doesn't know, it invents an answer with total confidence. Fine-tuning won't fix it, and re-training is out of reach. You need the model to look the answer up — and prove where it looked.

This project is that lookup, built properly. Two Markdown documents are split into retrievable chunks three different ways — naive fixed-size windows, header-respecting structural chunks with a hybrid ### sub-split gate, or embedding-similarity "semantic" windows — embedded with nomic-embed-text and stored in a persistent ChromaDB collection. At query time a hybrid retriever runs BM25 keyword search and vector similarity in parallel and merges the two ranked lists with Reciprocal Rank Fusion. The top-5 chunks are injected into a strict grounding prompt, and gpt-oss:120b (Ollama Cloud) answers only from that context — citing [Source: doc, Section: …] per claim, or saying "I could not find an answer…" instead of hallucinating. The whole thing is a three-node LangGraph StateGraph with an error short-circuit, and a FastAPI visualizer that runs every step one at a time so you can watch chunk previews, per-stage ranking traces and stored vectors. And it doesn't just claim to work: a frozen 19-question golden set is scored with deterministic metrics (recall@k, citation coverage, must-term coverage, refusal accuracy) and diffed against a baseline — a red/green regression gate that stays LLM-free, with optional Ragas LLM-judged scoring on top.

The line that matters: retrieve honestly, answer only from what was retrieved, cite everything — and keep a scoreboard that turns green into red the moment quality slips.

The one-line principle

✂️ Chunks are the atoms of retrieval

A 500-character window slices through code blocks and merges unrelated topics; splitting at ## headers keeps every chunk a complete, self-contained section. The demo proves the same query returns fragments under one strategy and a clean, cited answer under the other. Chunking is not plumbing — it decides what the retriever can find.

🔀 Two retrievers beat one

Vectors find meaning ("auth setup") but miss exact tokens; BM25 finds exact tokens (MCPToolset, X-Goog-Api-Key) but misses paraphrases. Reciprocal Rank Fusion merges both ranked lists with 1/(rank + 60) — no score calibration needed, ranks are all that matter.

⚖️ Measure or it didn't happen

Every pipeline change is a hypothesis. A frozen golden set + deterministic metrics + a regression gate (🟢 ≤0.05 drop · 🟡 ≤0.15 · 🔴 >0.15) turns "feels better" into a verdict — and the UI diff table shows exactly which question regressed and why.

What is this project?

The RAG Documentation Assistant is a question-answering system for your own documentation. You feed it Markdown files; it learns them by splitting, embedding and storing them; then you ask questions in plain English and it answers using only those files — quoting the exact document and section behind every claim. If the answer isn't in the files, it says so instead of making something up.

Using it is three moves:

  1. Ingest — pick your Markdown files, choose a chunking strategy, press Run. Four steps later the knowledge base is built.
  2. Ask — type a question and watch five steps light up: embed the question, retrieve candidates, fuse the rankings, build the prompt, generate the cited answer.
  3. Check — run the evaluation suite: 19 frozen questions go through the live pipeline and are scored against a stored baseline. Green means the system is still as good as the day you measured it.

Think of it as a librarian who has read exactly two binders. Ask about something in the binders and you get the answer with the page number. Ask about anything else — the Stripe API rate limit, say — and the librarian doesn't guess: "I could not find an answer to this question in the provided documentation."

What does working with it look like?

The app is a FastAPI web app served at http://localhost:8000 with three tabs — 📥 Ingestion, 💬 Inference and 📊 Evaluation. Each tab draws its workflow as a chain of node cards; you run them one at a time (or all at once) and each node opens a detail panel showing exactly what it produced.

Step 1 — Build the knowledge base (Ingestion)

Pick files from docs/ (two are included: the healthcare MCP server guide and the AI-agents-vs-MCP documentation). Choose the chunking strategy — this is the single most important knob in the whole app — then run the four steps. The Chunk node shows a preview of every chunk with its word count and whether it contains a code block or table; the Store node shows the actual rows ChromaDB keeps: chunk id, metadata, an 8-value peek at the embedding vector, and the first 300 characters of text.

Step 2 — Ask a question (Inference)

Type a question like "What Python code do I need to connect an agent to the Maps MCP server?". The Retrieve node shows both candidate lists side by side — the BM25 keyword ranking and the vector-distance ranking — and the Rerank node shows the fused list with each chunk's rank in each list. The Generate node returns the answer with inline [Source: DOCUMENTATION.md, Section: …] citations, plus the extracted citation list and timing per step.

Step 3 — Prove it doesn't hallucinate

Ask about something the documents never mention — "What is the rate limit on the Stripe API?". The retrieved chunks will be irrelevant, and the model, constrained by its system prompt, replies: "I could not find an answer to this question in the provided documentation." This refusal is a designed, measured behavior — the evaluation suite has dedicated negative questions whose only passing answer is a refusal.

Step 4 — Keep it honest over time (Evaluation)

The golden set is generated by the LLM from your actual corpus (2 pairs per section), then hardened by three auto-filters: a closed-book check (if the LLM can answer the question with no context, it doesn't measure retrieval — reject), a grounding check (a judge pass verifies the reference answer is entailed by the source text — reject otherwise), and a dedupe pass (embed the questions locally; drop pairs >0.9 cosine-similar). You review and freeze the survivors — 19 pairs made the shipped set. From then on, every suite run replays them through the live pipeline and writes a snapshot; the gate diffs each snapshot against the stored baseline and emits 🟢 PASS / 🟡 WARN / 🔴 FAIL.

The one rule that matters: the generator is forbidden from using outside knowledge. Every claim must trace to a retrieved chunk, and every claim must carry a citation. That single constraint is what turns "an LLM that sounds right" into "a system you can actually trust" — and the citation-coverage metric checks the model kept its promise.

The 4-step workflow

1

Ingest — chunks are born here

Load → Chunk → Embed → Store. Choose the strategy first; everything downstream inherits its quality.

Character splitting cuts at fixed 500-char intervals with 50 overlap — the "bad" baseline that slices through code blocks and mixes topics. Structural (semantic) splitting cuts at ## headers, and any section over 400 words is sub-split at ### boundaries — every chunk is a complete section, code blocks and tables stay intact. The embedding-semantic strategy groups sentences by cosine similarity percentile with no headers required. Two included documents yield ~60–70 character chunks vs ~18–22 structural chunks — fewer pieces, each one whole.

2

Ask — retrieval does the heavy lifting

Embed query → retrieve candidates → RRF rerank → augment → generate.

The question is embedded with the same model as the corpus, then two searches race: BM25 over all chunk texts (exact tokens win) and cosine vector search with a 2× overfetch (meaning wins). RRF merges the rankings — a chunk ranked #1 by BM25 and #2 by vector gets a better fused score than a chunk ranked #1 by only one list. Top-5 survive into the prompt with their source labels attached.

RetrieverWhat it's good atWhat it misses
🔎 Vector onlyParaphrases, meaning, "how do I…" questionsExact identifiers like MCPToolset or X-Goog-Api-Key
🔤 BM25 onlyExact function names, config keys, error stringsSynonyms, conceptual matches
🔀 Hybrid + RRFBoth — a top hit in either list surfaces in the fused listNothing material — this is the default
3

Ground — the prompt is a cage

System prompt forbids inference; user message carries every chunk with its source label.

The prompt builder labels every chunk [Chunk 1 - doc | section] and appends the question. The system prompt states the citation format, the refusal sentence, and "do not infer, guess, or use external knowledge." In the UI you can edit this prompt live — which is exactly how you A/B a stricter or looser grounding policy, then re-run the suite to see if citation coverage moved.

4

Gate — snapshots vs. baseline

Run the suite → snapshot JSON → diff → 🟢🟡🔴 verdict.

Each snapshot freezes the full config (strategy, retriever, top_k, models, corpus size), the per-question metric rows and the latency profile. The gate watches recall, citation coverage, must-term coverage, refusal accuracy (drops) and latency (slowdowns): any quality metric down more than 0.05 is a 🟡, more than 0.15 a 🔴. LLM-judged Ragas metrics ride along for information but never influence the verdict — the gate stays deterministic and reproducible.

Why this matters: RAG systems degrade silently — a new document, a swapped embedding model, an "innocent" prompt tweak. The gate turns each of those into a red flag the day it happens, not the day a user complains.

The LangGraph pipeline

The whole query-time flow is a compiled StateGraph over one shared RAGState TypedDict (query, retrieved_chunks, prompt, answer, error). Each node is a pure function state → partial state, each wrapped in try/except that writes a human-readable error string instead of raising. A conditional edge after retrieve_node short-circuits to END when retrieval failed — the graph fails fast and the caller gets one clean RuntimeError(state["error"]). 

# pipeline/graph.py — the whole wiring
graph.add_edge(START, "retrieve_node")
graph.add_conditional_edges("retrieve_node", _route_after_retrieve)
graph.add_edge("build_prompt_node", "generate_node")
graph.add_edge("generate_node", END)
return graph.compile()

def run_query(query: str) -> Answer:
    final_state = rag_graph.invoke({"query": query, "retrieved_chunks": [],
                                    "prompt": None, "answer": None, "error": ""})
    if final_state.get("error"):
        raise RuntimeError(final_state["error"])
    return final_state["answer"]

Chunking: three strategies, one contract

Every splitter returns the same Chunk dataclass, so downstream code never cares which strategy produced a chunk. The structural splitter is the production default: 

# chunking/semantic_splitter.py — structural + hybrid gate
h2_parts  = re.split(r'\n(?=## )', text)          # cut ONLY at header boundaries
h3_parts  = re.split(r'\n(?=### )', part)          # sub-split sections > max_words
# metadata per chunk: doc_title, section_title, subsection_title,
#                     chunk_index, strategy, word_count
# flags per chunk:    has_code_block ("```" in content),
#                     has_table ("|---|" in content)
StrategyCut ruleParams (defaults)Trade-off
characterFixed windows, content-blind500 chars, overlap 50Breaks code blocks and tables mid-syntax; mixes topics. The deliberate "bad" baseline.
structuralAt ## headers; oversized sections re-cut at ###max 400 words/sectionWhole sections, code intact — ~3× fewer, far better chunks.
semantic (embedding)Sentence windows grouped by cosine-similarity percentilebuffer 1 · percentile 95 · min 100No headers needed; slower (embeds during chunking); sections become derived labels, not real headings.
The comparator makes the cost visible: chunking/comparison.py runs both strategies over one document and counts broken code blocks (odd number of ``` fences) and broken tables (no complete header+separator row) per strategy — the two statistics that predict bad retrieval before you ever run a query.

Embeddings & storage

EmbeddingModel mirrors the SentenceTransformer interface (.encode(texts) → 2-D numpy array) but is backed by any OpenAI-compatible /v1/embeddings endpoint — by default local Ollama (http://localhost:11434/v1, model nomic-embed-text). Chat goes to Ollama Cloud (https://ollama.com/v1, gpt-oss:120b) — the split exists because the cloud plan serves chat models only, embeddings stay local.

ChromaDB stores each chunk as four fields — the store node shows the real rows so the claim is concrete: 

id:        "DOCUMENTATION.md_7"                    # doc_title + "_" + chunk_index
document:  "<first 300 chars of the chunk text…>"
embedding: [ 0.01234, -0.05678, … ]                 # full n-dim vector (768 for nomic)
metadata:  { doc_title, section_title, subsection_title,
             chunk_index, strategy, word_count }
  • Upsert semantics: re-ingesting a document first deletes its stale chunks (by doc_title) so no orphans survive from a previous strategy.
  • Persistence: PersistentClient(path="chroma_data") — the index survives restarts; load_collection() raises a clear "Run demo/02_ingest.py first" if empty.
  • Index: ChromaDB's built-in HNSW (auto-tuned m/ef_construct here) — see the swap-to-Qdrant note at the end for explicit control.

Hybrid retrieval: BM25 + vectors + RRF

One pass over the collection does three ranked lists. BM25 is rebuilt per query from all chunk texts (BM25Okapi over lowercase whitespace tokens — cheap at this corpus size, brutally effective on identifiers). Vector search overfetches top_k × 2 candidates. Reciprocal Rank Fusion then merges ranks, never raw scores: 

rrf_score(d) = Σ  1 / (k + rank_list(d))        # k = 60, ranks 1-indexed
             = 1/(60 + rank_bm25) + 1/(60 + rank_vector)
Why hybrid is the default: ask "How is authentication configured for the MCPToolset?" and vector search ranks a paraphrased chunk high but may drop the chunk literally containing X-Goog-Api-Key; BM25 does the opposite. RRF's fused list contains the union — the UI's Rerank node prints all three stages (bm25 / vector / fused, with per-chunk rank contributions) so you can see a chunk climb because two lists agreed.

The golden set

Generated from your corpus, not written by hand: 2 pairs per section (cap 8 sections), plus multi-hop pairs requiring two sections of the same doc, plus negative cases about plausible-but-absent topics. Then three auto-filters run before anything is saved: closed-book (LLM must answer NOT_IN_GENERAL_KNOWLEDGE with no context, else the question tests memory, not retrieval), grounding (a judge pass must rate the reference answer SUPPORTED by the source), dedupe (local embeddings, drop >0.9 cosine). Survivors go to a review list; freeze writes eval/golden_set.jsonl — 19 frozen pairs in the shipped set (15 section · 2 multi-hop · 2 negative), generated by gpt-oss:120b.

The regression gate

The shipped baseline (snapshot 438b82f3, corpus = 46 embedding-semantic chunks, hybrid, top-5): recall_at_k 1.0, recall_section 1.0, recall_multihop 1.0, first_relevant_rank 1.18, must_term_coverage 0.67, refusal_accuracy 0.5, mean 2.2 s / p95 3.2 s per question — 30 snapshots of history sit alongside it in eval/snapshots/.

Phase 2 — Ragas (optional, off by default)

Opt-in LLM judging adds faithfulness, context_precision and context_recall (judge model, default glm-5.3-flash on Ollama Cloud — fast and non-reasoning) and answer_relevancy (embedding-based, local nomic-embed-text). Hardened for Ollama quirks: sequential workers on Windows, per-metric fallback (one bad judge row yields null, never kills the suite), /v1 must be in the base URL because LangChain's ChatOpenAI posts verbatim. Ragas rows land in the snapshot and the diff table — but never move the gate verdict, by design.

Design decisions & trade-offs

  • BM25 rebuilt per query over the full corpus — trivially correct and fast at this scale (tens of chunks); a real deployment would move to an indexed keyword engine. The trade is deliberate: one file, zero infra.
  • RRF over raw score blending — BM25 scores and cosine distances aren't comparable; ranks are. Fusion needs no calibration, which is why rrf_k=60 is the only knob.
  • Deterministic gate first, LLM judge second — Phase 1 runs in seconds, costs nothing, and is reproducible; the expensive judge rides along optionally and can't flip a verdict.
  • Error strings over exceptions inside nodes — a failed retrieval ends the graph with one readable message instead of a stack trace through LangGraph internals; the UI surfaces it on the failing node.
  • Models as config, not code — chat (gpt-oss:120b @ ollama.com/v1) and embeddings (nomic-embed-text @ localhost:11434/v1) are both plain OpenAI-compatible HTTP; swapping either is a one-line env change.
  • HNSW auto-tuned (ChromaDB) today, tunable (Qdrant) tomorrow — production would pin m/ef_construct explicitly; the store.py interface makes that a drop-in swap with zero changes to nodes, graph or demos.
