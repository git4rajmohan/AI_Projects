🔗 Knowledge Graph Builder — User Guide

— From spreadsheets to a queryable knowledge graph in 4 steps

What Is the Knowledge Graph Builder?

The Knowledge Graph Builder is a web application that turns your spreadsheet files (CSV) and text documents (Markdown) into an interactive, visual knowledge graph — a network of things and the connections between them — and then lets you ask questions about that data in plain English.

Instead of manually writing database queries or hiring a graph expert, you simply:

  1. Pick the files you want to use
  2. Describe what you're trying to build in a sentence or two
  3. Let the app's AI agents figure out the structure
  4. Review, approve, and start asking questions
💡 In a nutshell

Think of it as a smart assistant that reads your data files, understands what kinds of things are in them (products, suppliers, customers, etc.), figures out how they're connected, builds a visual graph database, and then answers your questions by searching that graph — all powered by AI.

The 4-Step Workflow

1
Select Your Files & Describe Your Goal

You start by choosing which data files you want to include. The app shows a file browser so you can navigate folders and pick CSV, Markdown, or JSON files. You might, for example, select a folder containing products.csv, suppliers.csv, components.csv, and part_supplier_mapping.csv.

You also give the database a name (e.g., "furniture_project") and write a short description of what you want, such as:

"Build a product knowledge graph with suppliers, assemblies, and parts. I want to query which suppliers supply which parts for each product."

This description guides the AI — it tells the agents what matters to you so they can make smarter decisions about how to structure the graph.

2
AI Proposes a Structure (Schema)

When you click "Run Agent Pipeline", a team of AI agents goes to work. They read your files, look at the columns and data, and figure out:

  • What things (nodes) exist — e.g., Products, Suppliers, Components, Assemblies
  • How they're connected (relationships) — e.g., a Product CONTAINS Components, a Supplier SUPPLIES Parts
  • Which properties matter — e.g., product name, price, supplier location

The AI doesn't just guess once — it uses a refinement loop with three agents working together:

The AI refinement loop: propose → critique → validate, with retry until valid

The proposer creates a draft schema, the critic checks it for problems (missing files, wrong connections, etc.), and if the critic says "retry," the proposer tries again with the feedback. When the critic says "valid," the loop stops.

You see all of this happening live in the Agent Pipeline Activity log, with real-time progress updates as each agent does its work.

💡 What you see

The result is a JSON text box showing the proposed structure — which files become nodes, which become relationships, and what properties to include. You can read through it and even edit it manually before proceeding.

3
Build the Graph

Once you're happy with the proposed structure, you click "Build Graph." The app then:

  • Creates a new database in Neo4j (if it doesn't already exist) with the name you chose
  • Reads each CSV file and creates nodes (things) in the graph
  • Creates the connections (relationships) between those nodes
  • Shows you a live progress log so you can see what's happening
From spreadsheet to graph: each CSV row becomes a node, mapping files become relationships

When it's done, you get a summary showing how many nodes and relationships were created, broken down by type (e.g., 15 Products, 8 Suppliers, 42 SUPPLIES relationships).

⚠️ Note

This step requires a running Neo4j database. If Neo4j isn't available, the build will fail with a connection error. The app handles this gracefully and shows you the error.

4
Query & Explore

Now the fun part — you can ask questions in plain English! The app has another AI agent dedicated to answering your questions. When you type something like:

"Which suppliers provide parts for the Stockholm Chair?"

The query agent does the following behind the scenes:

  1. Looks at the current graph structure to understand what's available
  2. Translates your English question into a database query (Cypher)
  3. Runs that query against the graph database
  4. Reads the results and writes a clear, human-friendly answer
How question answering works: your question → AI translates to Cypher → Neo4j executes → AI summarizes the answer

You also get a visual graph explorer — an interactive canvas showing nodes as colored circles and relationships as lines between them. You can zoom in/out, drag nodes around, and see the overall structure of your knowledge graph at a glance.

Below the visualization, Graph Statistics cards show you counts for each node type and relationship type, plus the patterns (e.g., Product → SUPPLIES → Supplier).

Tips for Best Results

✅ Do
  • Be specific in your goal description — mention the entities and relationships you care about
  • Select all related files together — the AI needs to see the full picture to find connections
  • Review the proposed schema before building — you can edit the JSON to fix anything the AI got wrong
  • Use meaningful database names — e.g., furniture_graph instead of db1
  • Ask clear questions — "Which suppliers provide parts for product X?" works better than "tell me about suppliers"
⚠️ Avoid
  • Don't select unrelated files from different projects in the same run
  • Don't skip the goal description — it significantly improves the AI's schema proposals
  • Don't expect perfect results every time — the AI is smart but may need your review
  • Don't forget that Neo4j must be running for the build and query steps to work

Common Questions

What if the AI gets the schema wrong?

You can edit the JSON directly in the schema review box (Step 2). You can also click "Re-run Agents" to have the AI try again. If a file was missed, the app automatically tries to detect and add it using built-in heuristics.

Can I use my own data?

Yes! Use the file browser to navigate to any folder on your computer and select your CSV, Markdown, or JSON files. The app copies CSV files into Neo4j's import directory automatically (including via Docker docker cp if Neo4j runs in a container).

What happens to my data?

Your data is loaded into a Neo4j graph database running locally. Nothing is sent to external services except the AI model calls (which send file previews and your goal description to the LLM for schema proposal and query answering). The graph data itself stays in your local Neo4j.

Do I need to know Cypher or graph databases?

No! That's the whole point. The AI agents handle the translation between your plain-English questions and the database query language. You just type questions and read answers.

Architecture Overview

The Knowledge Graph Builder is a FastAPI backend serving a single-page HTML/JavaScript frontend, backed by a Neo4j graph database, with AI orchestration via Google ADK (Agent Development Kit) agents powered by an LLM through LiteLLM.

System architecture: 4-layer stack — Browser → FastAPI → Processing modules → Data stores

Backend Modules

app/main.py — FastAPI Web Server

The entry point. Defines all REST endpoints, Pydantic request models (ProposeRequest, BuildRequest, QueryRequest), and wires together the agent and graph builder modules.

EndpointMethodPurpose

/api/filesGETLists CSV/MD files in a folder with headers, row counts, and sample rows

/api/propose/streamPOSTSSE streaming version — sends live progress events as the LoopAgent runs, then a final result event

/api/graphGETReturns nodes + edges (up to 200) for the Canvas visualization
/api/queryPOSTRuns the ADK query agent — NL question → Cypher → execute → NL answer

Database Auto-Creation

_ensure_database_exists() checks if the requested database exists via SHOW DATABASES, creates it with CREATE DATABASE IF NOT EXISTS, and polls (up to 10 × 0.5s) until the database status is online.

SSE Streaming for Agent Progress

The /api/propose/stream endpoint uses StreamingResponse with media_type="text/event-stream". An asyncio.Queue bridges the agent's progress_callback to the SSE stream. Heartbeat events are sent on timeout to keep the connection alive. Event types: progress, result, error, heartbeat.

app/agents.py — Google ADK Agent Orchestration

Defines and runs the AI agents using Google's Agent Development Kit (ADK). Two pipelines:

1. Schema Proposal Pipeline (LoopAgent)

Sequence diagram: schema proposal LoopAgent with SSE streaming back to browser

The schema_refinement_loop is a LoopAgent with 3 sub-agents:

AgentTypeRoleTools
schema_proposal_agent LlmAgent Reads files, proposes node & relationship construction rules get_approved_user_goal, get_approved_files, get_proposed_construction_plan, sample_file, search_file, propose_node_construction, propose_relationship_construction, remove_node_construction, remove_relationship_construction
schema_critic_agent LlmAgent Validates proposal — checks uniqueness, missing files, wrong node/rel assignments. Returns "valid" or "retry" with feedback get_approved_user_goal, get_approved_files, get_proposed_construction_plan, sample_file, search_file
CheckStatusAndEscalate BaseAgent Non-LLM control flow — reads session.state["feedback"], yields EventActions(escalate=True) if "valid" is found, stopping the loop — (deterministic)

Agent State Management

State keys are shared via ADK's InMemorySessionService:

  • approved_user_goal — dict with kind_of_graph and description
  • approved_files — list of selected file paths
  • proposed_construction_plan — the accumulating plan dict, updated by tools
  • feedback — the critic's output (written via output_key="feedback")

2. Query Pipeline (LlmAgent)

The query_agent is a single LlmAgent with two tools:

ToolPurpose
get_schema_context(database) Queries Neo4j for node labels, properties, and relationship types (excludes __-prefixed internal labels). Returns a text schema description.
execute_cypher(cypher_query, database) Runs a Cypher query against the specified Neo4j database and returns results as a list of dicts (values truncated to 200 chars).

The agent's instruction tells it to: (1) get the schema, (2) write a Cypher query with LIMIT 25, (3) execute it, (4) summarize results in natural language. Relationship direction hints are embedded in the instruction (e.g., Product-[:INCLUDES_FEATURE]->Feature).

Runner Execution

run_schema_proposal() and run_query_agent() are async convenience functions that create an InMemorySessionService, a Runner, and iterate over runner.run_async() events. The schema proposal function also:

  • Streams progress via progress_callback (supports async callbacks)
  • Attaches _file_paths mapping to the plan for the builder
  • Auto-detects missing rules via _auto_detect_rule() when the LLM skips files
  • Auto-detects reference relationships via _auto_detect_reference_relationships()

Auto-Detection Fallbacks

When the LLM doesn't create rules for every file, two heuristic functions fill the gaps:

  • _auto_detect_rule(file_path, plan) — reads CSV headers, checks if columns match existing node unique columns (→ relationship) or if the filename contains keywords like "purchase", "partnership", "mapping" (→ relationship). Otherwise creates a node rule with the first _id-suffixed column as the unique key.
  • _auto_detect_reference_relationships(plan) — scans node rules for foreign-key columns (matching another node's unique_column_name, or patterns like {label}_id) and auto-creates relationship rules (e.g., PRODUCES, BELONGS_TO).

app/graph_builder.py — Graph Construction & Data Access

Handles the deterministic (non-AI) parts of the pipeline:

Schema Proposal (Direct LLM)

propose_schema() is a fallback that calls the LLM directly (OpenAI client) with a structured system prompt defining the JSON plan schema. Used when ADK agents are not available. Parses the response, strips markdown fences, and extracts JSON via regex fallback.

Graph Construction

build_domain_graph(plan, database, progress_callback) executes the plan:

Graph construction flow: plan → separate rules → MERGE nodes → MERGE relationships → summary
  1. Separates node rules and relationship rules from the flat plan dict
  2. For each node rule: copies the CSV to Neo4j's import dir, runs LOAD CSV WITH HEADERS ... MERGE (n:Label {unique_col: row.unique_col}) SET ...
  3. For each relationship rule: copies CSV, resolves from_node_property/to_node_property from node rules, runs MATCH (from:LabelA {prop: row.col}) MATCH (to:LabelB {prop: row.col}) MERGE (from)-[r:REL_TYPE]->(to) SET ...
  4. Returns summary with nodes_created, relationships_created, and errors

CSV Import Path Resolution

_copy_csv_to_neo4j_import() handles the complexity of getting CSV files into Neo4j's import directory (required for LOAD CSV):

  • Preserves subfolder structure (e.g., project1_furniture/products.csv)
  • Tries docker cp into running Neo4j containers (searches by name and ancestor filter)
  • Creates parent directories inside the container via docker exec mkdir -p
  • Falls back to common local Neo4j import paths (~/.neo4j/import, C:/neo4j/import, etc.)

Statistics & Visualization Data

  • get_graph_stats(database) — returns node counts by label, relationship counts by type, and relationship patterns (from-label, type, to-label, count). Excludes __-prefixed internal labels.
  • get_graph_data(limit, database) — fetches up to N nodes (excluding Chunk, Document, and __-prefixed labels) with display names resolved from common properties (name, product_name, title, etc.). Also fetches edges between those nodes (up to 500).

app/query_engine.py — Direct LLM Query (Fallback)

A non-ADK fallback for query answering. Uses the OpenAI client directly in a 3-step pipeline:

Query pipeline: both ADK (primary) and direct-LLM (fallback) paths
  1. Cypher generation — system prompt with schema context + relationship direction hints → LLM generates Cypher (strips markdown fences, LIMIT 25 enforced)
  2. Execution — runs the Cypher against Neo4j, collects results (values truncated to 200 chars)
  3. Answer generation — sends question + Cypher + results to LLM → natural-language summary

The main /api/query endpoint uses run_query_agent() from agents.py (ADK) instead, but answer_question() here serves as the direct-LLM alternative.

Frontend (static/index.html)

A single-page application built with vanilla HTML/CSS/JavaScript (no framework). Key features:

  • 4-step stepper UI — Select Files → Review Schema → Build Graph → Query & Explore
  • File browser — calls /api/browse to navigate the filesystem, supports folder navigation (Up button) and multi-file selection
  • SSE agent progress log — connects to /api/propose/stream via EventSource, displays live agent activity with color-coded entries (start, done, iteration, tool, error) and a progress bar
  • Schema editor — editable JSON textarea for the proposed construction plan
  • Build progress log — shows Cypher execution progress from /api/build
  • Canvas graph visualization — custom 2D canvas renderer with zoom/pan/drag, color-coded node types, legend, and force-directed-style layout
  • Database selector — dropdown populated from /api/databases, allows switching between Neo4j databases
  • Query results — renders the NL answer (with HTML support), the generated Cypher query, and raw result tables

LLM Integration

The app uses LiteLLM (LiteLlm(model=LLM_MODEL)) for ADK agents and the OpenAI Python client for direct calls. The model is configured via environment variables: 

OPENAI_API_KEY  = ollama-cloud-proxy     # dummy key for proxy
OPENAI_API_BASE = http://127.0.0.1:11435/v1  # Ollama cloud proxy
OLLAMA_MODEL    = openai/gpt-oss:120b        # LLM model name

An Ollama cloud proxy (ollama_cloud_proxy.py at the workspace root) translates between OpenAI format (expected by LiteLLM and the OpenAI client) and Ollama's native API format. The proxy handles:

  • /v1/chat/completions → Ollama /api/chat
  • /v1/embeddings → Ollama /api/embed
  • Strips openai/ model prefix
  • Translates tool definitions (ensures parameters is a dict)
  • Translates messages: OpenAI tool_calls → Ollama format; parses arguments string → dict
  • Flattens array content ([{type:"text",text:...}] → plain string)

Construction Plan Schema

The plan is a flat dict where each key is a rule name and each value has a construction_type:

{
  "Product": {
    "construction_type": "node",
    "source_file": "products.csv",
    "label": "Product",
    "unique_column_name": "product_id",
    "properties": ["name", "price", "category"]
  },
  "SUPPLIES": {
    "construction_type": "relationship",
    "source_file": "part_supplier_mapping.csv",
    "relationship_type": "SUPPLIES",
    "from_node_label": "Supplier",
    "from_node_column": "supplier_id",
    "from_node_property": "supplier_id",
    "to_node_label": "Component",
    "to_node_column": "component_id",
    "to_node_property": "component_id",
    "properties": ["lead_time"]
  },
  "_file_paths": {
    "products.csv": "/abs/path/to/products.csv",
    "part_supplier_mapping.csv": "/abs/path/to/part_supplier_mapping.csv"
  }
}

Pydantic models (NodeRule, RelationshipRule, ConstructionPlan) are defined in graph_builder.py for validation, though the agent-produced plans are consumed as plain dicts.

Running the App

Key Design Decisions

  • ADK LoopAgent for schema proposal — iterative refinement (propose → critique → validate) produces better schemas than a single LLM call. The critic's output_key="feedback" automatically writes to session state, which the proposer reads on the next iteration.
  • Auto-detection fallbacks — LLMs can skip files or miss foreign keys. The heuristic auto-detect functions ensure every selected file gets a construction rule and reference relationships are inferred from column name patterns.
  • SSE streaming — the schema proposal loop can take 30+ seconds. SSE keeps the user informed with live progress instead of a blank loading spinner.
  • Multi-database isolation — each project gets its own Neo4j database, preventing data collisions between different graph builds.
  • Docker-aware CSV import — docker cp handles the common case where Neo4j runs in a container without volume binds for the import directory.
  • Vanilla JS frontend — no build step, no framework dependency. The single index.html file is served directly by FastAPI.
  • Dual query paths — ADK query_agent (primary) and direct LLM answer_question() (fallback) provide resilience if ADK has issues.
